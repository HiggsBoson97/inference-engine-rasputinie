## Loop delimitation (addresses, first/last instruction, unroll factor)

The steady-state body is delimited by the single backward branch in `k_full<0,0>`:

```
	s_and_not1_b32 exec_lo, exec_lo, s24                       // 0000000065B4: 917E187E
	s_cbranch_execnz 65216                                     // 0000000065B8: BFA6FEC0 <_Z6k_fullILi0ELi0EEvPKhPKiPfPyiiii+0x1bc>
```

`s_cbranch_execnz` SIMM16 = `0xFEC0` = −320 dwords; target = next-PC `0x65BC` + 4·(−320) = **`0x60BC`**,
which agrees with objdump's own `+0x1bc` (0x5F00 + 0x1BC). That instruction is in turn the branch
destination of nothing else, so the body is exactly the loop from `0x60BC` to `0x65B8`:

```
first:  s_delay_alu instid0(VALU_DEP_2)                            // 0000000060BC: BF870002
next:   v_mad_u64_u32 v[24:25], null, 0x6e, v22, v[8:9]            // 0000000060C0: D6FE7C18 04222CFF 0000006E
   ... 193 instructions ...
last:   s_cbranch_execnz 65216                                     // 0000000065B8: BFA6FEC0
```

- Address range **0x60BC–0x65B8**, 0x500 = **1280 bytes**, **193 instruction words** (independent
  count: `awk '/60BC/,/65B8/' full.dis | grep -c //` → 193). 1280/193 = 6.6 B/word: several
  instructions carry 4-byte literals (`v_mad_u64_u32 …,0x6e,…`, `s_addc_u32 s5,s5,lit(0x0)`), so a
  byte-size count would overstate; the count is by instruction word, not by byte.
- **Unroll factor = 8.** The body contains exactly **8 `v_dot4_i32_i8`** and 8 distinct x-vector
  loads at byte offsets −28, −24, −20, −16, −12, −8, −4, 0 from one moving base, i.e. the eight 4-weight
  groups of one 32-weight sub-block, fully unrolled. The `b`-loop itself is **not** further unrolled:
  one copy of the body exists between the preheader (`s_cbranch_execz 337` at 0x6078) and the loop
  exit at 0x65BC. Stride is inside the body:
  `v_add_nc_u32_e32 v23, 32, v23` (b += 32) and `v_dual_add_nc_u32 v22, 4, v22` (b>>3 += 4).
- **This is the `k_full<0,0>` / `LAY=0` body**, confirmed by the field offsets, not by reading the C++:

| field | disassembly | offset | `Off<0>` |
|---|---|---|---|
| qs (8 B) | `global_load_b64 v[26:27], v[26:27], off offset:2` | +2 | 2 |
| qh (1 B) | `global_load_u8  v32, v[28:29], off offset:66` | +66 | 66 |
| sg (4 B) | `global_load_b32 v28, v[28:29], off offset:74` | +74 | 74 |
| sc (1 B) | `global_load_u8  v29, v[30:31], off offset:106` | +106 | 106 |
| d (2 B) | `global_load_d16_b16 v25, v[24:25], off` | +0 | 0 |

The eight dots, with addresses:

```
v_dot4_i32_i8 v33, v30, v31, v33   // 000000006218
v_dot4_i32_i8 v33, v24, v30, v33   // 000000006290
v_dot4_i32_i8 v33, v24, v30, v33   // 00000000630C
```

One `v_dot4_i32_i8` is one **wave** instruction: 32 lanes × 4 int8 weights = **128 weights**.
Eight of them per iteration = 32 weights per lane = 1024 weights per wave per iteration.

Sanity: 8 masks × 6 sign ops = 48 ✓; 8 gathers ✓; 8 x-loads ✓; 8 dots ✓.

**Shape of the cost.** The dot is 4 % of the body. The sign path alone (48) is 25 % and costs six
instructions per four weights — five SWAR mask-build ops plus one nibble extract, per dp4a.
Non-VALU classes are 41 % of the body: 21 global-memory instructions, 27 SALU, 31 `s_delay_alu`;
only **114 of 193 are VALU arithmetic**. `s_waitcnt` alone appears 19 times — the body is a
long chain of individually-issued loads with per-load scoreboard waits, which is why the compiler
also emits 31 `s_delay_alu` dependency markers.

### `k_full<0,2>` NOSGN — 608.2 GB/s — 115 instructions / 32 weights / lane, 8 dots

`0x86B8`–`0x899C`, closed at 115 (dot 8, index 36, address 7, field loads 4, gather 11, x-loads 10,

`0x7DC0`–`0x82F8`, 187 instructions (residue 0) — only **6 fewer** than the real kernel, because the

## Slot weighting (raw / per-instruction cost / all-class)

Per 32 weights per lane. `n` is quoted per 4 weights in both unit systems so the two can never be
confused again.

| normalisation | k_full | k_read | NOSGN | units |
|---|---:|---:|---:|---|
| **raw instruction words** | 193 | 56 | 115 | wave instructions / 32 w-lane |
| **lane-instruction count per 4 weights** (what the note's wording says) | **24.125** | 7.00 | 14.375 | lane-instr per 4 w |
| **VALU-only** (what the note's definition literally scopes to) | 114 → 14.25 | 32 → 4.00 | 63 → 7.88 | lane-instr per 4 w |
| **slots at measured per-instruction cost** (`dp4a` = 2 slots, half rate, no dual-issue; all else 1; one VOPD carries 2 ops in 1 slot) | 201 | 56 | 123 | slots / 32 w-lane |
| **all-class slots** (VALU 114 + global-mem 21 + SALU 27 + `s_delay_alu` 31 — issue slots are shared) | 193 | 56 | 115 | slots / 32 w-lane |
| **wave-normalised: slots per 4 weights** = slots·4 / 1024 weights | **0.754** (0.785 with `dp4a`=2) | 0.219 | 0.449 | slots per 4 w |

The all-class row is the one the hardware sees: an `s_waitcnt` or a `global_load_b32` consumes the
same issue slot as a `v_and_b32`. Counting only VALU understates the body by 41 %.

## Reconciliation (wave instr/s vs slot rate; occupancy; the n question answered)

Measured 516.4 GB/s on 110 bytes per 256 weights → `BPW = 0.4296875` B/weight.

```
weights/s        = 516.4e9 / 0.4296875            = 1201.8 G weights/s
wave-iterations/s = 1201.8e9 / 1024               =   1.1736 G /s      (1024 w per wave iteration)
slots/s used      = 1.1736e9 × 193                = 226.5 G slots/s
fraction of 470.7 G/s                             =   0.481
```

**The instruction-derived wave rate reproduces the measured GB/s only at 48.1 % issue utilisation.**
Stated the way the brief's verification asks: issue-saturated, this census predicts

```
470.7e9 slots/s × (1024/193 weights per slot) × 0.4296875 B = 1073 GB/s
1073 / 516.4 = 2.08×        ← the factor, stated explicitly
```

So the census and the measurement differ by **2.08×**, and that factor is the result, not an error:
the kernel is issuing on 48 % of its slots at the measured rate. To sustain 48 % each SIMD32 needs
≥ 2.08 waves resident (one wave issues ≤ 1 instr/cycle), i.e. ≥ 3 waves at typical residency — a
completely ordinary occupancy, not a saturated machine. Even hitting the 776 GB/s wall would need
only 340.4 G slots/s = **72.3 %** of 470.7.

Same arithmetic on the ablation, using each kernel's own census:

| kernel | insns/32w | GB/s | slots/s used | issue util | % of 776 wall |
|---|---:|---:|---:|---:|---:|
| `k_read` | 56 | 717.7 | 91.3 G | 19.4 % | 92.5 % |
| `k_full` NOSGN | 115 | 608.2 | 159.0 G | 33.8 % | 78.4 % |
| `k_full` | 193 | 516.4 | 226.5 G | **48.1 %** | 66.6 % |

Memory utilisation is above issue utilisation in every row — 92.5 vs 19.4, 78.4 vs 33.8, 66.6 vs
48.1. The nearer constraint is never the issue port.

### What `n` actually is

The note's formula is `ceiling = 4 · slots · (bpw/8) / n`, with `n` *defined* as "VALU instructions
per 4 weights". That formula is only dimensionally valid if **one issue slot advances 4 weights**.
On this ISA one issue slot advances **128** weights (`dp4a`, 32 lanes × 4). The factor of 32 that
this omits is exactly the wave.

Because the formula is short by 32, it can only produce sane numbers for `n` near unity, and `n`
was therefore never counted — it was **solved for**:

```
note constant      4 · 470.7e9 · 0.4296875          = 809.08 GB/s at n = 1
n implied by 516.4 = 809.08 / 516.4                 = 1.5668   ← note's "1.57"
n at the 776 wall  = 809.08 / 776.0                 = 1.0426   ← note's "1.04"
```

Both of the note's numbers are reproductions of two measurements, to four figures. They are not a
census of anything.

Correct normalisation (128 weights per slot per instruction):

```
ceiling = 128 · slots · (bpw/8) / n_lane      with n_lane = lane-instr per 4 weights
        = 128 · 470.7e9 · 0.4296875 / 24.125  = 1073 GB/s      (= 2.08 × measured, as above)
```

So:

- **As a lane-instruction count**, `n` would be **24.1** (all classes) or **14.25** (VALU only) — not
  1.57. The emitted code is 15.4× the note's figure.
- **As an issue-slot count** (slots per 4 weights, the only normalisation in which the note's 1.04
  budget is meaningful), `n` is **0.754** (or 0.785 with `dp4a` at half rate) — 2.08× *below*
  1.57 and **27.7 % below the 1.04 budget**, not 50 % above it.
- `n = 1.57` is neither. It is the residual of the 32× unit error, and its sign is inverted: under
  its own budget the kernel is *under* the instruction budget, with 28 % of the slot capacity still
  spare at the measured rate.

**The decisive internal check — `n` does not track instruction count.** The note asserts `n` is
proportional to instructions per 4 weights. Two ablations the project already measured say it is not:

| variant | census insns/32w | measured GB/s | n solved from the note's own formula | what `n` should have done |
|---|---:|---:|---:|---|
| `k_full` | 193 | 516.4 | 1.567 | — |
| NOSGN | 115 (−40.4 %) | 608.2 | 1.330 (−15.1 %) | −40 % |
| gather → arithmetic | 187 (−3.1 %) | 493.5 | 1.640 (**+4.7 %**) | −3 % |

A quantity that falls 15 % when its supposed cause falls 40 %, and *rises* 5 % when its supposed
cause falls 3 %, is a memory-side residual being labelled as an instruction count.

## Verdict (supports / refutes H-2)

**Supports H-2** (mechanism confirmed, with one refinement). The census closes at 193 instruction
words per 32 weights per lane with zero unclassified residue, 8 `dp4a` and 1024 weights per wave
iteration, so one issue slot buys 5.31 weights, not 4: the note's `4·slots·(bpw/8)/n` is 32× short
per instruction, and `n = 1.57` is the back-solved residual of that error (`809.08/516.4 = 1.5668`),
not a count of anything in the ISA. Correctly normalised, the same measurement corresponds to 0.754
issue slots per 4 weights against a 1.04 budget — 28 % *under* budget — and to 48.1 % issue
utilisation of the note's own 470.7 G/s model, i.e. 2.08× below the rate at which this instruction
stream would saturate issue. The refinement to the ledger's wording: `n` is not literally a
lane-instruction count either, because the code's real lane-instruction count is 24.1; the note's
`n` is a slot count in disguise. Consequently "IQ3_S is instruction-bound, so no memory-side
optimisation counts" is not supported by this evidence — VALU issue is the *third* nearest limit,
behind the 776 GB/s wall (66.6 %) and behind whatever costs the kernel the other 28 % of the read
floor that `k_read` reaches (516.4 / 717.7 = 0.72). The sign path is real work (48 of 193 instructions, 25 % of the body)
and is worth attacking on its own terms, but it is not what the budget arithmetic says it is.
Remaining candidates the census points at, for the counter capture to arbitrate: the 19 `s_waitcnt`
+ 31 `s_delay_alu` (43 % of the body is wait machinery on individually-issued global loads) and 21
global-memory instructions per 32 weights against `k_read`'s 5.
