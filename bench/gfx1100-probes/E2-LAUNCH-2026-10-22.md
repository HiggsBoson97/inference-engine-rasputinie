# Per-launch bandwidth on gfx1100: is it real?

**Answer: there is no per-launch bandwidth penalty in steady state. The marginal
cost of an extra kernel launch is 2.5–2.9 µs — the same as launching an empty
kernel. What looks like a penalty is two unrelated effects:**

1. **a ~3 ms clock-ramp wake-up** that costs the first one to three launches after
   an idle GPU, and is **completely removed by pinning the DPM performance level**
   (launch 0 after a 3 s idle: 2.13 ms → 0.73 ms);
2. **a footprint cliff at ~800 MiB per launch**, costing ~200–230 µs per launch,
   which is **clock-independent** (identical with clocks pinned) and is what the
   old "eight back-to-back 1 GiB launches = 641 GB/s" measurement actually hit.

A realistic per-tensor decode step (401 launches, 11.2955 GB) reaches
**712 GB/s / 60.6 tok/s**, and its entire 8 % deficit against the wall is
`401 × 3.3 µs = 1.31 ms` of launch overhead. Fusing to 2–4 layers per launch
removes it (**774 GB/s / 65.8 tok/s**). Fusing 8 layers per launch is **worse than
per-tensor** (691 GB/s) because 1.3 GB launches sit on the wrong side of the
footprint cliff.

Host: `rasputin`, card `0000:07:00.0` (headless), `HIP_VISIBLE_DEVICES=1`,
`hipcc --offload-arch=gfx1100 -O3`, hipEvent timing, warm-up discarded, median
reported. All logs in `~/e2/log_*.txt`; every number below is one of those logs.

|---:|---:|---:|---:|---:|---:|
| 1 | 4 GiB | 738.5 | **755.0** | 5.689 |
| 2 | 2 GiB | 708.8 | **723.0** | 5.940 |
| 4 | 1 GiB | 654.1 | **665.9** | 6.450 |
| 8 | 512 MiB | 753.8 | **769.5** | 5.582 |
| 16 | 256 MiB | 755.2 | **770.2** | 5.576 |
| 32 | 128 MiB | 739.9 | **753.5** | 5.700 |
| 64 | 64 MiB | 710.0 | **722.1** | 5.948 |
| 128 | 32 MiB | 722.2 | **732.7** | 5.862 |
| 256 | 16 MiB | 671.7 | **677.6** | 6.339 |

The curve is **not monotonic**, which is why a linear fit over all points is
meaningless (and why the original probe's reasoning went wrong):

```
FIT t(N) = a + N*c
  all 9 points        : c =  1.7 µs/launch   R² = 0.21     <- nonsense, trend is not linear
  N >= 8  (<=512 MiB) : c =  2.9 µs/launch   R² = 0.89     <- run B
  N >= 32 (<=128 MiB) : c =  2.5 µs/launch   R² = 0.85
  repeat run (N>=8)   : c =  2.6 µs/launch   R² = 0.88
```

**The fitted per-launch cost is 2.5–2.9 µs, identical to the 2.45–2.98 µs cost of
launching an empty kernel.** 401 launches of a decode step therefore cost
`401 × 3 µs ≈ 1.2 ms`, and that is exactly the deficit measured in §4.

Everything that does not fit `c ≈ 3 µs` is a per-launch *footprint* effect, not a
per-launch *count* effect:

| N | bytes/launch | excess over the 770 GB/s rate | µs/launch |
|---:|---:|---:|---:|
| 1 | 4 GiB | +113 µs | 113 |
| 2 | 2 GiB | +364 µs | 182 |
| 4 | 1 GiB | **+874 µs** | **218** |
| 8 | 512 MiB | +6 µs | 0.7 |
| 16 | 256 MiB | −0 µs | 0.0 |
| 32 | 128 MiB | +124 µs | 3.9 |
| 64 | 64 MiB | +372 µs | 5.8 |
| 128 | 32 MiB | +286 µs | 2.2 |
| 256 | 16 MiB | +763 µs | 3.0 |

The N=2/4 rows are the only ones far from `c ≈ 3 µs`, and they are the only rows
with ≥1 GiB per launch. §1b isolates why.

### 1b. Reproducing the original observation, and what it really was

```
HIP_VISIBLE_DEVICES=1 ./launch orig 7        # log_orig.txt — same 8 GiB, different splits
```

| delivery | GB/s | per-launch ms (median / min / max) |
|---|---:|---|
| 8 × 1 GiB | **653.9** | 1.528 / 1.411 / 1.648 |
| 4 × 2 GiB | 708.3 | 2.802 / 2.798 / 3.035 |
| 1 × 8 GiB | 754.7 | 11.376 |

The original 641 GB/s reproduces at 653.9. It is **not** launch cost — the same
process, same buffer, same address range, split differently, moves 100 GB/s.

The decisive version of that comparison — same 8 GiB, *more* launches, faster
(`./launch sizesub <MiB> <N> 7`, `log_sizesub.txt`):

| delivery of exactly 8 GiB | launches | GB/s |
|---|---:|---:|
| 8 × 1024 MiB | 8 | **665.7** |
| 32 × 256 MiB | 32 | **770.8** |
| 16 × 512 MiB | 16 | **770.0** |
| 1 × 8192 MiB | 1 | 754.7 |

(653.9 and 665.7 are the same 8 × 1 GiB effect measured in two processes with
different arena sizes; the spread is arena/offset, the cliff is the same.)

**Four times as many launches, 16 % more bandwidth.** If per-launch cost were the
mechanism, 32 launches would be the worst case; it is the best. Only the 1 GiB
launches are slow, and there are fewer of those in the fast rows.

### 1c. One launch, varying size — the footprint cliff

```
HIP_VISIBLE_DEVICES=1 ./launch size 8192 7            # log_size.txt
HIP_VISIBLE_DEVICES=1 ./launch sizelist 512,...,3072 5 # log_sizelist.txt
```

| bytes/launch | GB/s | kernel ms | note |
|---:|---:|---:|---|
| 8 MiB | 212.3 | 0.040 | grid too small to saturate (latency-bound, see caveat) |
| 16 MiB | 596.6 | 0.028 | |
| 32 MiB | 664.7 | 0.050 | |
| 64 MiB | 1065.9 | 0.063 | **Infinity Cache** (80 MB, fits) |
| 128 MiB | 837.4 | 0.160 | partially cache-resident |
| 256 MiB | 745.3 | 0.360 | |
| 512 MiB | 749.4 | 0.716 | |
| **768 MiB** | **773.6** | 1.041 | **at the wall, zero overhead** |
| **896 MiB** | **649.4** | 1.447 | **cliff** |
| 1024 MiB | 652.0 / 664.1 | 1.647 | cliff |
| 1152 MiB | 676.9 | 1.785 | |
| 1280 MiB | 686.9 | 1.954 | |
| 1536 MiB | 701.9 | 2.295 | |
| 2048 MiB | 707.8 | 3.034 | |
| 3072 MiB | 744.0 | 4.330 | |
| 4096 MiB | 739.0 | 5.812 | |
| 8192 MiB | 755.5 | 11.370 | |

The transition is sharp: **768 MiB runs at the wall (773.6), 896 MiB collapses to
649 and then recovers slowly with size.** Quantified at fixed clocks
(`log_sizelist_perfhigh.txt`, so power throttling is out of the picture), the
cliff is **~230 µs of lost time that a launch only pays if its footprint exceeds
~800 MiB**, whose relative weight then decays as the launch gets longer:

| bytes/launch (clocks pinned) | GB/s | actual ms | at 773 GB/s | excess |
|---:|---:|---:|---:|---:|
| 768 MiB | 773.5 | 1.041 | 1.041 | **~0** |
| 896 MiB | 650.1 | 1.445 | 1.215 | **+230 µs** |
| 1024 MiB | 665.5 | 1.614 | 1.389 | **+224 µs** |
| 1536 MiB | 702.1 | 2.294 | 2.084 | +210 µs |
| 2048 MiB | 722.5 | 2.972 | 2.779 | +194 µs |
| 4096 MiB | 754.7 | 5.691 | 5.558 | +133 µs |
| 8192 MiB | 772.4 | 11.121 | 11.113 | +8 µs † |

† the 8 GiB point is *not* evidence against the cliff: at that size the probe's
rotating offset has run out of room (arena 9 GB minus an 8 GiB slice leaves only
0.4 GB to rotate through), so every rep re-reads essentially the same window and
walks the page tables once. At auto clocks the same 8 GiB launch gives 755.5 GB/s
/ 11.370 ms = **+257 µs** over the wall, which is the cliff *plus* the ~2 % energy
throttle that only shows on 11 ms kernels (removed by pinning: 772.4).
The 8 × 1 GiB and 16 × 512 MiB rows of §1b are the clean side-by-side: 1 GiB pays
the cliff, 512 MiB does not, and both are TLB-cold by construction.

It is **not** occupancy-, grid- or ILP-sensitive (`./launch diag 1024 5` →
`log_diag1024.txt`: 18 configurations from `grid=SM*1 ilp=4` to `grid=SM*32 ilp=16`
all land at 660–665 GB/s), and **not** the memory clock:
`./launch sizelist ... ` with `power_dpm_force_performance_level=high` gives
650.1 at 896 MiB and 665.5 at 1024 MiB — the same cliff (`log_sizelist_perfhigh.txt`).

Cause not identified at the microarchitectural level. It behaves like a
first-touch table-walk cost for a range larger than some coverage, and it
disappears on subsequent passes over the same range — which is exactly what the
existing `gemv.cpp` result shows: 1.04 GiB footprint, 1 pass = 651.9 GB/s,
8 in-kernel passes = 752.5 GB/s. Same cliff, same size, different kernel.

## 2. Does the penalty survive a hot GPU?

```
HIP_VISIBLE_DEVICES=1 ./launch hot 4 8 warm|cold|spin|gaps 6     # log_hot8.txt
HIP_VISIBLE_DEVICES=1 ./launch hot 4 64 warm|cold|spin|gaps 6    # log_hot64.txt
GAP_US=<us> ./launch hot 4 64 gaps 5                            # log_gapladder64.txt
HIP_VISIBLE_DEVICES=1 ./launch wake 512 12 nosleep|cold|spin     # log_wake_*.txt
```

| condition (4 GiB total) | N=8 (512 MiB/launch) | N=64 (64 MiB/launch) |
|---|---:|---:|
| warm, back-to-back | **769.8** | **722.5** |
| cold: 3 s idle before the burst | 472.4 | 477.6 |
| after a 2 s spin kernel | 602.0 | 600.5 |
| 1 ms host gaps between launches | 492.2 | 66.8 |

The cold numbers are a **fixed ~3.0–3.5 ms per burst** (4 GiB at 769.8 = 5.58 ms;
at 472.4 = 9.09 ms), identical at N=8 and N=64 — i.e. it is a wake-up, not a
per-launch cost. The 1 ms-gap row is duty cycle (a 96 µs kernel every 1 ms = 10 %),
not a penalty; see the ladder below.

### 2b. Where the cold penalty lives: the first three launches

`./launch wake 512 12 <cond>` (12 × 512 MiB, per-launch timings, `log_wake_*.txt`):

| launch # | no sleep `log_wake_nosleep` | 3 s idle `log_wake_cold` | after 2 s spin `log_wake_spin` | 3 s idle, **clocks pinned high** |
|---:|---:|---:|---:|---:|
| 0 | 0.7008 ms (766) | 2.1329 ms (252) | 4.4538 ms (120) | **0.7315 ms (734)** |
| 1 | 0.7019 (765) | 1.8689 (287) | 1.6478 (326) | 0.7154 (751) |
| 2 | 0.7003 (767) | 1.3060 (411) | 0.9873 (544) | 0.7112 (755) |
| 3 | 0.7007 (766) | 0.7054 (761) | 0.7003 (767) | 0.7113 (755) |
| 4+ | 0.700 (766) | 0.705 (761) | 0.700 (767) | 0.711 (755) |

(The pinned-clock row was taken with `power_dpm_force_performance_level=high`;
`wake` was re-run per condition, and the two cold runs agree to within 0.1 ms on
launch 0.)

**This is the answer to "is it a warm-up artefact": yes for the cold case, and the
cause is the clock/power ramp.** Pinning `power_dpm_force_performance_level=high`
removes the entire ~1.4 ms transient on launch 0 (252 → 734 GB/s) and the ~3.3 ms
burst total (11.71 ms → 8.63 ms). Note that a compute-only spin kernel makes it
*worse* (4.45 ms on launch 0) than plain idle: high sclk with zero memory traffic
leaves the memory path in its lowest state.

In steady state — the only regime a decode loop ever sees — **every launch from
#0 to #11 runs at 766 GB/s.** There is no per-launch ramp at all.

### 2c. Gap ladder: the GPU does not lose its fast state between launches

4 GiB as 64 × 64 MiB (kernel-only ≈ 97 µs), host busy-wait between launches:

| gap | GB/s | implied idle per launch | of the gap requested |
|---:|---:|---:|---:|
| 0 | 722.5 | 0 | — |
| 100 µs | 652.5 | ~20 µs | 100 µs |
| 200 µs | 330.7 | ~115 µs | 200 µs |
| 500 µs | 132.9 | ~430 µs | 500 µs |
| 1000 µs | 66.8 | ~951 µs | 1000 µs |

Loss = the idle time you asked for, minus queue look-ahead. **No additional
penalty per launch boundary.**

## 3. Clock sampling during the run

`~/e2/sampler.py` reads hwmon `freq1_input` (sclk), `freq2_input` (mclk) and
`power1_average` (PPT) from the host as fast as sysfs allows.

```
python3 sampler.py 2                      # idle baseline
./launch loop small256.txt 6 &            # 256 x 16 MiB launches, repeating
python3 sampler.py 4.5                    # sample during it
```

| | idle | during the launch loop |
|---|---|---|
| samples | 365 attempts, **only 20 readable** (GPU runtime-suspended) | 856 / 856 readable |
| median sampling interval | 5.5 ms | **5.3 ms** |
| sclk | median 36 MHz (18–1023) | **median 2930 MHz** (2807–2937) |
| **mclk** | 96 MHz (80 % of samples), 456 (15 %), 772 (5 %) | **1249 MHz in 100 % of samples** (1 distinct value) |
| PPT | 21–97 W | median 240 W, max 242 W |
| achieved | — | 662.9 GB/s (`log_loop_small.txt`) |

**Findings:**

* **`1249 MHz` is the *top* `mclk` step, not the idle step.** Sampling every second
  after a run (`log_idle_decay.txt`): t=0 s → **1249 MHz**, t=1 s and for the next
  24 s → **96 MHz**, sclk 0 MHz, 18 W. So 1249 is what the card reports in the
  first moments after activity (and what `hipGetDeviceProperties().memoryClockRate`
  returns) — which is where the project's "the card idles at memclock 1249 MHz"
  came from. The card's real idle step is **96 MHz**, and after 3 s of idle it is
  firmly at 96. That is what the first launch of a burst has to climb out of, and
  why pinning the performance level deletes the transient in §2b.
* **During sustained launch traffic `mclk` sits at its top step in 100 % of 856
  samples**, with `sclk` at 2930 MHz and 240 W. So the 662 GB/s achieved by a
  256-launch step is **not** a memory-clock deficit. The clock is already at max.
* **Limit, stated plainly:** the sysfs read floor is ~5 ms and a 1 GiB launch is
  1.6 ms, so **this sampler cannot resolve the ramp inside individual launches.**
  It is too slow to answer the question directly. The question is answered
  causally instead, by §2b: pinning the performance level deletes the transient,
  which is only possible if the transient *is* the DPM ramp.

## 4. The number that matters: a realistic decode step

Launch shapes are taken from the real model, not invented:
`~/local-inference/models/gguf/Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf` parsed with
`~/e2/gguf_manifest.py` (851 tensors, 64 layers, arch `qwen35`, total
**11.760551936 GB** — the 11.76 GB figure).

* Real matmul tensors per layer: `attn_qkv` 27.85 MB, `attn_gate` 16.71 MB,
  `ssm_out` 16.71 MB, `ffn_gate` 25.76 MB, `ffn_up` 22.98 MB, `ffn_down` 28.55 MB
  (+ small `ssm_alpha/beta/conv1d`), 122–203 MB per layer.
* Step set = every 2-D tensor ≥1 MB with both dims ≥16 — everything a token
  multiplies against, which includes `output.weight` (715.16 MB) — excluding
  `token_embd.weight` (407 MB) because that is a row gather, not a stream. That is
  **401 launches, 11.2955 GB**, median tensor 25.8 MB, min 1.68 MB, max 715 MB.
  (The brief assumed ~200 launches; this 64-layer hybrid attention/SSM model has
  ~6.3 matmuls per layer, hence 401. A 201-launch variant is measured in §5 so the
  "~200 kernels" case is covered either way.)
* Offsets are packed into an 11.3 GB arena in touch order (`emit.py` → `seq_tensor.txt`).

```
HIP_VISIBLE_DEVICES=1 ./launch decode seq_tensor.txt tensor 1  7    # log_decode_step1_all.txt
HIP_VISIBLE_DEVICES=1 ./launch decode seq_tensor.txt tensor 10 3    # log_decode_step10.txt
```

| | one step | 10 steps back-to-back |
|---|---:|---:|
| achieved | **712.3 GB/s** | **714.7 GB/s** |
| ms/step | 15.858 | 15.804 |
| tok/s (`GB/s × 1e9 / 11.76e9`, per the project convention) | **60.6** | **60.8** |
| tok/s from the bytes actually read (11.2955 GB) | 63.1 | 63.3 |
| % of the 776 GB/s wall | **91.7 %** | 92.1 % |

Identical at 1 and 10 steps → the step is at steady state; nothing accumulates.
(Also confirms the numbers are not Infinity-Cache-inflated: 11.3 GB per step, and
the cache is 80 MB.)

**Where the 8 % goes — it is launch cost, exactly:**

```
11.2955 GB at the 776.4 GB/s wall        = 14.55 ms
measured                                  = 15.86 ms
excess                                    =  1.31 ms
401 launches x 3.3 us                     =  1.31 ms
```

Grid policy is not the cause: forcing `grid = SM*8` or `SM*16` for every launch
instead of the size-adaptive grid gives 714.3 / 715.1 GB/s (`log_decode_grid.txt`),
i.e. +0.6 % — the deficit is the launch count.

## 5. Does fusing layers help? Yes — up to a point, and past it, no.

Same 401 tensors, same 11.2955 GB, regrouped so each launch covers *k* whole
layers (`seq_l1..l64.txt`). One step, 7 reps (`log_decode_step1_all.txt`):

| grouping | launches | bytes/launch | GB/s | ms/step | tok/s | excess vs wall | µs/launch |
|---|---:|---:|---:|---:|---:|---:|---:|
| per-tensor | 401 | 28 MB | 712.3 | 15.858 | **60.6** | 1.309 ms | 3.3 |
| 2 tensors | 201 | 56 MB | 725.9 | 15.561 | 61.7 | 1.012 ms | 5.0 |
| 1 layer | 65 | 174 MB | 760.9 | 14.845 | 64.7 | 0.296 ms | 4.6 |
| **2 layers** | **33** | **348 MB** | **774.2** | **14.590** | **65.8** | **0.04 ms** | 1.3 |
| **4 layers** | **17** | **690 MB** | **773.8** | **14.597** | **65.8** | 0.05 ms | 2.9 |
| 8 layers | 9 | 1.35 GB | **691.4** | 16.337 | 58.8 | 1.789 ms | **199** |
| 16 layers | 5 | 2.4 GB | 737.0 | 15.326 | 62.7 | 0.778 ms | 156 |
| 32 layers | 3 | 4.1 GB | 762.3 | 14.818 | 64.8 | 0.269 ms | 90 |
| 64 layers | 2 | 5.9 GB | 775.5 | 14.565 | 65.9 | 0.017 ms | 8 |

Repeated 10× back-to-back, the same ordering holds with no drift
(`log_decode_step10.txt`): 714.7 / 726.1 / 760.8 / **774.1** / 773.7 / 691.0.

The 8-layer row is the §1c cliff, in the wild: each launch is 1.35 GB, pays
~199 µs, and the step loses 1.79 ms — **worse than per-tensor dispatch.** It
recovers only when the launch is big enough to amortize the cliff again
(32/64 layers).

## Recommendation

**Fuse at layer scope: 2–4 layers per launch (17–33 launches per step).**

* 774 GB/s = **99.7 % of the measured wall**, 65.8 tok/s — versus 712 GB/s /
  60.6 tok/s for per-tensor dispatch.
* The gain is 8 %, and it is entirely the 1.3 ms of launch cost that 401 launches
  buy. Nothing about the kernels themselves improves.
* Fusing a layer needs no data movement: a per-layer block→(tensor, row-block)
  index table is enough to run `attn_qkv / attn_gate / ssm_out / ffn_gate /
  ffn_up / ffn_down` as one grid, because each matmul is an independent
  dot-product row and the shapes are known at load time.

**Do not fuse 8 layers per launch.** 1.3 GB per launch crosses the ~800 MiB
footprint cliff, costs ~200 µs per launch, and lands at 691 GB/s — *below*
per-tensor dispatch. Any plan that groups by "one launch per N layers" must keep
N small or the launch is bigger than 800 MiB.

**Per-tensor dispatch is viable**, contrary to the fear that motivated this
measurement. It costs 8 % (60.6 vs 65.8 tok/s) and it is the simplest plan. What
was never viable was assuming the *original* 641 GB/s — that number is a
1 GiB-footprint artefact, and the same probe gives 770 GB/s at 256–512 MiB.

**Per-tensor dispatch also does not need a warm-up protocol.** The only cold-start
cost is ~3 ms on the first 1–3 launches after an idle GPU (one-time per burst,
not per token), and it disappears with `power_dpm_force_performance_level=high`.

## What this corrects in the project's existing notes

1. **"Eight back-to-back 1 GiB launches gave 641 GB/s, so there is a per-launch
   penalty."** There is no per-launch penalty. 8 × 1 GiB reproduces at 653.9 GB/s
   because 1 GiB per launch sits on the wrong side of a footprint cliff at
   ~800 MiB. The same 8 GiB delivered as **32 × 256 MiB reaches 770.8 GB/s** —
   four times the launch count, 16 % more bandwidth.
2. **"Any bandwidth number from a kernel shorter than ~3 ms under-reports this
   card by 10–15 %."** Wrong. A 256 MiB launch is 0.36 ms and reaches **770 GB/s**;
   a 512 MiB launch is 0.72 ms and reaches **769**. Duration is not the variable —
   footprint is. The old rule happened to fit because the two sizes compared were
   1 GiB (cliff) and 6 GiB (no cliff).
3. **"The card idles at memclock 1249 MHz."** 1249 MHz is the top step and the
   value the card reports immediately after activity; true idle is **96 MHz**
   within one second (`log_idle_decay.txt`). Under sustained load mclk is at 1249
   in 100 % of samples.
4. **"The per-launch penalty is unidentified, DPM is the leading candidate."**
   DPM is the cause of the *cold-start* transient only (§2b, proven by pinning
   clocks). It is not the cause of the launch-count effect, which is 3 µs of
   launch cost.

## Caveats, stated as caveats

* These are **read streams, not GEMV**. The launch-count arithmetic is independent
  of the kernel body, and the existing `gemv.cpp` result (752.5 GB/s = 97 % of the
  wall on one tensor) says the ALU in a fused dequant-GEMV is not the limiting
  factor — but the decode-step numbers here are an upper bound for the *dispatch
  pattern*, not a measurement of the real GEMV per-tensor rate.
* Sub-16 MiB launches in `./launch size` are depressed by the grid policy
  (one iteration per thread), not by hardware; the aggregate decode number and
  its exact agreement with `401 × 3 µs` show the launch pattern is what is
  being measured.
* The physical cause of the ~800 MiB cliff is **not** established. It is
  reproducible across two kernels (`launch` read stream, the existing `gemv.cpp`),
  independent of clock, grid, ILP and occupancy, and costs ~200–230 µs at the
  onset, less as the launch grows, and nothing once the page tables are warm from
  a previous pass over the same range. Table-walk / TLB coverage is the leading
  hypothesis and is untested.
* One self-inflicted out-of-bounds read (`launch wake` with an arena smaller than
  N × slice) caused an amdgpu GPU reset at ~22:45; the driver recovered on its own
  and the guard is fixed. The §1 table is the run taken *after* that reset
  (`log_sweep4_run2.txt`); `log_sweep4.txt` is the earlier run and agrees to 1.5 %.
