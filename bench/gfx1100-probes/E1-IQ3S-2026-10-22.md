# IQ3_S: is codebook addressing the bandwidth cap? — FINAL

`~/e1/RESULTS.md`, 2026-10-22. Card `AMD Radeon RX 7900 XT`, PCI `0000:07:00.0`
(`HIP_VISIBLE_DEVICES=1`, headless). `hipcc --offload-arch=gfx1100 -O3`.
Reference wall **776 GB/s** (`bench/gfx1100-probes/WALL-2026-10-22.md`).
Model file opened `O_RDONLY`; no repo file modified.

Sources: `~/e1/iq3s_valid.cpp` (all measurements), `~/e1/mkmanifest.py` (tensor
selection + block-stride validation), `~/e1/gguf_probe.py` (type histogram),
`~/e1/find_scales.py` (locates the fp16 field from the data).

**Verdict in one line: the codebook gather costs nothing; the per-weight sign
bit costs ~12 % of the memory wall; and the lossless 4-bit expansion needs 100.4 %
of the wall to break even, so it is rejected.**

---

## 1. Per-row validity table

Footprint **1.0700 GiB** (30 real IQ3_S tensors `blk.*.ffn_up/gate.weight`,
`[5120,17408]`, concatenated read-only). Grid `336 x 256` (2688 warps), `rp=4`,
median of 3 runs. Cross-checked at 3.2101 GiB and 4.2841 GiB (buffer replicated),
single pass.

Every row carries a data-dependent checksum (order-independent sum, replayed on the
host from the same bytes); a GB/s figure above the wall is also an automatic
INVALID. All 10 rows passed in all 3 runs.

| mode | verdict | GB/s | % of 776 | footprint |
|---|---|---:|---:|---|
| `wall_flat` — aligned `uint4` stream of the same bytes (control) | VALID | 668.5 | 86.1 % | 1.0700 GiB |
| **`read`** — real block addressing, 32 weights/iteration | VALID | **717.7** | **92.5 %** | 1.0700 GiB |
| `exp_read` — load-only floor, expanded layout | VALID | 687.2 | 88.6 % | 1.6148 GiB |
| **`full`** — real dequant + dot | VALID | **516.4** | **66.6 %** | 1.0700 GiB |
| `nogather` — table load replaced by pure ALU | VALID | 493.5 | 63.6 % | 1.0700 GiB |
| `full_nosgn` — sign decode removed | VALID | 608.2 | 78.4 % | 1.0700 GiB |
| **`exp`** — lossless 4-bit expansion + dot | VALID | **618.1** | **79.7 %** | 1.6148 GiB |
| `exp16` — fp16 scale per 32 weights (lossy 2.5e-02) | VALID (ungated) | 630.0 | 81.2 % | 1.7120 GiB |
| `wall_1pass` — control, 1 pass = 1.6 ms (short-kernel biased) | VALID | 653.3 | 84.2 % | 1.0700 GiB |
| `exp_nosgn` — expansion, sign decode removed | VALID | 784.5 | 101.1 % | 1.6148 GiB |

Large-footprint confirmation (single pass, no repeat traffic to cache):

| footprint | `wall_flat` | `read` | `full` | `exp` | `exp_nosgn` |
|---|---:|---:|---:|---:|---:|
| 3.2101 GiB | 726.4 | 694.2 | 517.0 | 626.6 | 786.1 |
| 4.2841 GiB | 736.0 | 702.7 | 514.9 | 619.7 | 779.6 |

Correctness: `full` vs an independent fp64 CPU reference **4.834e-06** worst
relative error (0 rows above 2e-3); `exp` vs the **same** fp64 reference
4.834e-06; `exp` vs `full` **0.000e+00 — bit-identical**, which is the losslessness
proof. `exp16` is not lossless (2.535e-02) and buys 12 GB/s, so it is dropped.

Run-to-run spread at fixed config is ±3 % (`read` 716.7–739.4) — card clock
behaviour, not the probe. A high-grid regime was voided during development: at
5376x1024 threads each thread touched ~13 quads and the compiler collapsed the
`rp` passes, reporting 1112–1784 GB/s; those rows are **discarded** and the
`read`-mode check is now used as the invalidity detector.

## 2. The three ablations

Each is computed only from rows that passed the gate, expressed against the
layout's own floor `read` = 717.7 GB/s and against the 776 wall.

| ablation | GB/s | % of wall | what it isolates |
|---|---:|---:|---|
| gather: `full` − `nogather` | **−22.9** (removing it is *slower*) | −3.0 % | the cost of the 8 dependent 512-entry codebook loads per 32 weights — **zero**; the "no-gather" kernel is not faster, so the load is fully hidden |
| sign: `full_nosgn` − `full` | **+91.8** | +11.8 % | the per-weight conditional-negate (mask build + `(x^m)+1` on 4 packed bytes, ×8 per 32 weights) — already branch-free SWAR, so this is the *irreducible* cost of 1 sign bit per weight |
| index + dot: `read` − `full_nosgn` | **+109.5** | +14.1 % | 9-bit index assembly from `qs`+`qh`, the two misaligned scalar-load pairs, and the 8 `v_dot4_i32_i8` — everything except the sign |
| total: `read` − `full` | +201.3 | +25.9 % | dequant + dot as a whole (28 % of the reader's rate) |

Same sign cost, isolated again where nothing else is in the way:
`exp_nosgn − exp` = **+166.4 GB/s (21.4 % of wall)**.

## 3. Whole-file estimates (ESTIMATE)

**Assumption: the 7.560 GiB of non-IQ3_S bytes (69 % of the file) stream at
752 GB/s**, the rate the 4-bit dequant-GEMV class already demonstrated. Only the
IQ3_S portion is measured.

| packaging | IQ3_S rate used | ESTIMATE tok/s |
|---|---:|---:|
| **IQ3_S as-is** | 516.4 measured | **56.0** |
| IQ3_S with the sign decode made free | 608.2 measured | 59.6 (+6.4 %) |
| lossless 4-bit expansion (5.1875 bpw) | 618.1 measured | 50.7 (**−9.5 %**) |
| 4.1875 bpw signed-nibble repack (lossy, needs re-quantization) | 784.5 est. | 60.8 (+8.6 %) |

Which types are likely to fall short of 752: **IQ3_XXS (98 B) and IQ2_S (82 B)**
carry *more* codebook gathers per byte than IQ3_S — IQ3_XXS folds signs into the
codebook (8 gathers per 32 weights, no sign plane), IQ2_S uses a 1024-entry grid
plus a separate 32 B sign plane — and at 2.56–3.06 bpw they also spend more ALU
per byte. Since the gather measured free, their shortfall should come from the
ALU-per-byte term rather than from indirection, but they are the two to measure
next; Q4_K adds a min term inside the accumulation and IQ4_XS's 16-entry
register-synthesised table is the closest existing shape to the 752 recipe.

## 4. The finding that inverts the prior

**The gather is not the cost. Sign decode is.**

- Reading the real 110-byte blocks at 32 weights per iteration reaches **717.7
  GB/s = 92.5 % of the wall** (739.4 best run; 702.7 at 4.28 GiB against a 736.0
  aligned-stream control). Block addressing is free, even though 110 B is not a
  multiple of 4 and every group's index/sign fields are only 2-byte aligned.
- Deleting the codebook load entirely makes the kernel **slower** (516.4 → 493.5,
  −22.9 GB/s): the 2 KB table sits in L1 and its latency is fully hidden behind
  the dp4a chain. There is no "dependent gather" bottleneck to attack.
- Removing the sign decode returns **+91.8 GB/s (+11.8 % of wall, +17.8 % relative,
  516.4 → 608.2)** in the IQ3_S layout and **+166.4 GB/s (+26.9 % relative)** in
  the expanded layout. This is with an implementation that is *already*
  branch-free SWAR (`mask = ((bits*0x10204080 & 0x80808080) >> 7) * 0xFF`, then
  `(x^m)+1`, no table, no branch), so the number is the intrinsic cost of applying
  32 sign bits per 32 weights, not a bad-codegen artefact.

**Reconciliation with the literature's "+23 % from branch-free SWAR at identical
bit width":** same phenomenon, same magnitude, different target. Their +23 % is
the gain from making the *same* bit-width cheaper to decode; here, deleting the
work that the branch-free form still has to do is worth +17.8 % (IQ3_S shape) to
+26.9 % (4-bit shape). Both point at instruction count per weight, not bytes and
not indirection — which is why a 3.44 bpw format loses 25.9 % of the wall while a
4.5 bpw format loses ~3 %.

## 5. Expansion: rejected

The lossless expansion needs **1.5091x the bytes** (166 B vs 110 B per 256
weights) and delivers **1.197x the speed** (618.1 vs 516.4), so it costs
**1.226–1.260x the wall time** (1.26x on the medians; 1.226x in the best run).

| | bytes | GB/s | IQ3_S portion per token |
|---|---:|---:|---:|
| serve IQ3_S as-is | 3.393 GiB | 516.4 | **7.06 ms** |
| lossless expansion | 5.120 GiB | 618.1 | **8.86 ms** |

Break-even requires **779.4 GB/s = 100.4 % of the 776 wall**. Even with the sign
decode made free — `exp_nosgn` at 784.5, i.e. already *at* the wall — the ratio is
1.5091 x 516.4 / 784.5 = **0.994, a tie**. The expansion cannot pay for its own
size under any implementation; the only packaging that beats as-is is a 4.1875 bpw
signed-nibble repack (x1.218 bytes, no codebook, no sign plane, ~60.8 tok/s), and
that is a *lossy re-quantization*, not a repack of these bytes.

File size: IQ3_S 3.393 GiB → 5.120 GiB; whole file 10.953 → **12.680 GiB
(+15.8 %)**; if all i-quants were expanded, 14.19 GiB (+3.24 GiB).

## 6. What the first kernel slice should optimise

Priority order, using measured headroom (all against the 776 wall, IQ3_S layout):

| # | target | available | expected realistic gain |
|---|---|---:|---:|
| 1 | **Sign path.** Pre-spread the sign plane at load so a mask costs 1 AND (not mul+and+shr+mul), and negate the *activation word* once for the 32-weight group instead of 8 times per group. Aim: 6 → 2 ops per 4 weights. | +91.8 GB/s | **+40 to +70 GB/s (+5 to +9 % of wall)**; ~+4 to +6 % tok/s |
| 2 | **Index assembly + dot.** Merge the two misaligned scalar-load pairs into one aligned 16 B per-lane read of a reshaped block (a *load-time permutation only*, bytes unchanged), then 8 dp4a with no per-group index math. | +109.5 GB/s | **+40 to +60 GB/s**; ~+4 to +5 % tok/s |
| 3 | **Configuration.** Grid/block sweep (GRIDMUL 4–32, BLK 128–512) moved `full` by <2 %; 31 registers = full occupancy. Do not tune this. | ~+10 GB/s | <1 % |
| 4 | **Codebook.** Leave it alone. Measured cost ≈ 0; `nogather` is *slower*. | 0 | 0 |

What would falsify this recommendation: (a) a kernel with the *same* instruction
count per weight reaching >600 GB/s, which would mean `full`'s 516 is a
scheduling/occupancy artefact rather than issue-bound — unlikely, since the
occupancy sweep moved it <2 % and it uses 31 registers; (b) an IQ3_S dequant that
holds ~600 GB/s *without* removing sign work, which would mean the sign cost I
measured is an artefact of my particular cneg sequence rather than intrinsic;
(c) an independent IQ3_S implementation on this card in the 700s, which would mean
the 25.9 % dequant penalty is mine, not the format's.

## 7. Caveats I cannot resolve

1. **`exp_nosgn` reports 101.1 % of the 776 wall** (784.5; 779.6 at 4.28 GiB on a
   single pass, where no repeat traffic can be cached, L2 being 96 MB). Its
   checksum matches exactly, so it did read the 1.61 GiB it counts. Two
   explanations remain and I did not separate them: **(a)** the 776 wall is
   slightly conservative in the hot state for a three-plane 16 B/lane pattern
   (in-session controls measured 736.0 for a single aligned stream at 4.28 GiB, so
   the wall is pattern-dependent within ~7 %), or **(b)** a residual counting error
   of ~1.5 % in that one kernel. (a) is better supported, because a 6.9 GiB
   single-pass read cannot be cached, and because 776 was itself the doc's median
   with a 777.4 maximum. The decision does not depend on it: the break-even test
   uses `full` and `exp`, both well under the wall, and even at 784.5 the
   expansion only ties.
2. **Codebook content is a placeholder** of the documented shape (512 entries x 4
   magnitudes). The ordering cannot be recovered from the file plus our docs, and
   no bandwidth number depends on it (any 2 KB table with this access pattern
   performs identically). Consequence: the dequantized *values* are self-consistent
   and land on a plausible magnitude scale (mean |w| 0.0145, rms 0.0172) but are
   not guaranteed to be the model's intended weights.
3. The **4-bit multiplier law `d x (1+2n)`** is assumed (the docs give the field
   width, not the law). One multiply per 32 weights, so no bandwidth number moves;
   losslessness holds under any law applied identically to both paths.
4. **Which `qh` bit / sign bit belongs to which weight** is a convention,
   undetectable from the data. It permutes values, not their statistics.
5. Field order *is* resolved by the data: `d` at offset 0 (positive and finite for
   100 % of blocks, median 7.28e-05; every other even offset is a 50/50 coin
   flip). The `d@108` reading of the docs' field *listing* gives non-finite scales
   and |w| ≈ 1e6.

## 8. Exclusion compliance

No llama.cpp source, binary, constant or derived code was used to produce any
number in this report. The codebook is a placeholder generated by my own LCG, not
copied from any implementation; the block semantics are arithmetic on the field
sizes in `docs/research/2026-10-22/03c-gguf-quant-layouts.md` plus the data in the
GGUF itself. The early clone was deleted before any measurement was taken;
`~/e1/` contains only `iq3s_valid.cpp`, `iq3s_probe.cpp` (superseded, its
high-grid regime is documented as void), `mkmanifest.py`, `gguf_probe.py`,
`find_scales.py`, `RESULTS.md`.
