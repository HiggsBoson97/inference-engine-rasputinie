# The memory wall, measured twice — 2026-10-22

Two independent runs on PCI `07:00.0` (headless), `hipcc --offload-arch=gfx1100 -O3`,
`HIP_VISIBLE_DEVICES=1`, hipEvent timing, warm-up discarded.

**Result: the read wall is ~776 GB/s. The 619 GB/s this project has used since its
first session is a kernel artefact, not the card.**

## Source: `bw2.cpp`

```
HIP_VISIBLE_DEVICES=1 RP=4 ./bw2 6144 5      # 6 GiB buffer
```

| kernel | GB/s |
|---|---|
| `uint` (4 B/lane) ×8 in flight | 763.3 |
| `uint2` (8 B/lane) ×8 | 766.4 |
| `uint4` (16 B/lane) ×8 | 766.6 |
| `uint4` non-temporal | 767.0 (max 775.5) |
| **`uint4` ×8, 4 in-kernel passes, same footprint** | **776.4** (max 777.4) |
| copy, counted read+write | 618 (NT store 658) |

Load width per lane is worth ~0 %: 4, 8 and 16 B/lane all land at 763–767.
Occupancy is worth little once ILP is present: `SM*1` gives 750, `SM*64` gives 758.
Slab-per-block addressing costs 7 % against grid-stride (704 vs 757).

## Why 619 was wrong

Same card, same session, only the kernel's duration changed:

| 1 GiB buffer | 1 pass (1.6 ms) | 4 passes (6.4 ms) |
|---|---|---|
| read GB/s | 662 | 746 |

| 6 GiB buffer | 1 pass (8.6 ms) | 4 passes (33 ms) |
|---|---|---|
| read GB/s | 749 | 768 |

**Any bandwidth number taken from a kernel shorter than ~3 ms under-reports this
card by 10–15 %.** The repo's 619 came from 1.6 ms passes with a serial
accumulator dependency and no unrolled loads (`bw.cpp`).

> **Correction, 2026-10-22 (E2).** The *duration* rule above is **wrong**. A
> 256 MiB launch lasting 0.36 ms reaches **770 GB/s**, so short kernels are fine.
> The real variable is **footprint per launch**, with a cliff at roughly
> **800 MiB**: the same 8 GiB delivered as 32×256 MiB gives 770.8 GB/s, as
> 8×1 GiB gives 665.7. The cliff costs ~230 µs per launch and is
> clock-independent — a TLB/page-walk hypothesis, untested. The 1 GiB single-pass
> result in the table above is that cliff, not a duration effect.
> `bench/gfx1100-probes/E2-LAUNCH-2026-10-22.md` §1.

## The fused dequant-GEMV: `gemv.cpp`

4-bit weights, 32-weight blocks, fp16 scale plane (4.06 bpw), one warp per row,
`v_dot4_i32_i8` via inline asm, 1.04 GiB footprint (400 000 × 5120):

```
HIP_VISIBLE_DEVICES=1 ./gemv 400000 5120 soa 8 5 64 8 1
```

| variant | GB/s |
|---|---|
| 1 pass | 651.9 |
| **8 in-kernel passes** | **752.5** (max 756.0) |
| quants only, no scale, no ALU | 832.7 |
| correctness vs host reference | **worst rel err 2.646e-07**, 0 rows > 2e-3 |

**A fused 4-bit dequant-GEMV reaches 97 % of the measured read wall on this card,
with the arithmetic verified to 2.6 × 10⁻⁷.** That is the single most important
number in the project: the kernel thesis is not a hypothesis.

## What this does to every ceiling

Weights 11.76 GB (IQ3_S), single card:

| sustained GB/s | ms/token | tok/s |
|---|---|---|
| 619 (the old, wrong wall) | 19.0 | 52.6 |
| 776 (weights-only ceiling) | 15.15 | **66.0** |
| 650 (realistic sustained in a decode loop) | 18.1 | **55** |
| 466 (60 % of the real wall — a defensible floor) | 25.2 | 39.6 |

## Two caveats that must not be lost

1. **The synthetic 4-bit layout is not IQ3_S.** IQ3_S addresses codebooks with
   8 dependent scalar grid loads per 32 weights. Third-party RDNA evidence
   (`docs/research/2026-10-22/03-bandwidth.md` §7) shows IQ3_S at 236 GB/s
   effective against Q4_0's 409 — a 42 % penalty. **If that holds here, the
   quant choice re-opens**, and it is the reason to own the load layout (O1b):
   the codebook can be pre-expanded at load time, trading size for load
   independence.
2. **The per-launch penalty is a clock wake-up, not a launch cost.** A burst
   after 3 s idle loses ~3.3 ms in its first three launches; with
   `power_dpm_force_performance_level=high` the transient disappears entirely.
   **Correction (E2): the clock claim below was inverted — 1249 MHz is the *top*
   memory step, not idle. Idle is 96 MHz.** A decode loop keeps the card hot, so
   this costs nothing in steady state; it costs everything for a single cold
   measurement.
