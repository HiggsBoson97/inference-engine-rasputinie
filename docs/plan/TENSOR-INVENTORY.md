- closes exactly: **True**
- tensors contiguous as `offset[i] + bytes[i] == offset[i+1]`: **True**

- every quantised tensor's size equals its block formula exactly (no inter-tensor padding): **True**
- every quantised tensor's `ne[0]` is a multiple of its block width, so every row starts on a block boundary: **True**
- types whose block layout could not be verified: none

The block-formula check is what makes the type column trustworthy: if a
tensor's byte count equals `params / block_weights * block_bytes` for its
declared type, the declared type and the offset arithmetic agree.

original table (lifted from Strata's reader) did not name it. The name comes
from the ggml type registry; the arithmetic confirms the layout independently:

unnamed id.

Two widths carry a design decision worth reading twice: `attn_q` is 12288, which
is 24×256 **twice** — the query and its output gate in one matrix, so the gate is
not a separate tensor and not a separate GEMV. `attn_qkv` is 10240 = 2×(16×128) +
6144 — q and k at 16 heads of 128 feeding the conv and the delta rule, v at 48
heads of 128 feeding the state. Both are single GEMVs with a concatenated output.

## 3b. Parameter count

| file | parameters | vs the 27.78 B in docs/01 |
|---|---|---|
| IQ3_S (trunk) | 26,895,998,464 (26.896 B) | -0.884 B |
| IQ3_S-mtp | 27,320,697,856 (27.321 B) | -0.459 B |

The gap is accounted for, not mysterious: the `-mtp` file's 27.32 B plus the
0.466 B of the BF16 visual tower in `mmproj-Qwen3.8-27B-BF16.gguf` (931,146,528 B
/ 2) comes to 27.79 B — the 27.78 B in `docs/01-models.md`. That figure therefore
counts the MTP layer **and** the visual tower, and it is the right number for
a model card, not for a decode budget.

For the weight budget: the text trunk alone is **26.90 B parameters**, of which the embedding and head are 2.54 B (9.5%) and the MLP 17.11 B (63.6%). The vision
tower is never read during text decode and must not appear in a decode budget.

## 7. Shape uniformity

Every role has exactly one shape across all its layers: the 64 layers'
attention and MLP shapes are **identical**. A kernel can be written for one
shape per role and dispatched on role alone — no per-layer specialisation is
needed for shape. Types, however, are *not* uniform (section 8), so the
dispatch key must be (role, type), not role.

The MTP layer keeps the same geometry: every tensor it adds for an existing role has the trunk's shape (**True**).

All shared tensors have the same type, shape and byte size in both files.
Their **payloads were not hashed** — that would read 12 GB twice and prove
nothing about the kernels. What the kernel set needs is that the same
(role, type, shape) triple appears in both, and it does.

What this adds to the kernel list:

- **One more full-attention layer** (index 64, kind `full+mtp`) with the trunk's shapes. The existing full-attention kernels run it unchanged.
- **A precision the trunk never uses.** Every matrix in that layer is Q6_K — 0.324 GiB of the 0.325 GiB added. The trunk carries IQ3_S, IQ4_XS, IQ3_XXS, Q4_K, IQ2_S, Q2_K, IQ2_XS, IQ2_XXS, BF16, IQ1_M, F32; Q6_K is in neither list. The GEMV set therefore needs a Q6_K path that exactly one layer exercises.

- **A 65th layer changes the loop bound, not the kernel set.** Layer count, not shape or type, is what the runtime has to parameterise.

## 10. What this fixes for the kernel list

1. **Shapes are uniform per role.** No shape-generic kernel is needed; a
   per-role kernel covers all 64 layers and the MTP layer.
2. **Types are not.** Every quantised role carries several types. The dispatch
   key is therefore `(role, type)` — 72 pairs in
   the base file. A single GEMV per role would silently fall back for half the
   layers.
3. **GDN is not a side quest.** The GDN-only tensors are 2.35 GiB (21.5%), and they are read on
   48 of the 64 layers. Any plan that ships full attention first covers 16.
4. **The fused projections change the kernel shape.** `attn_qkv` is 5120→10240
   (q and k at 16×128 plus v at 48×128), and `attn_q` is 5120→12288 (q at
   24×256 with its output gate fused). Neither is a plain square projection;
   both are one GEMV producing concatenated slices.
5. **Mixed precision inside one GDN block** (`ssm_alpha`/`ssm_beta` BF16,
   `ssm_a`/`ssm_dt` F32) means the GDN kernel takes both dtypes, not just the
   quantised path.
6. **Speculation costs one more quant type.** The MTP layer is entirely Q6_K, which the trunk never uses. Either the GEMV set grows a Q6_K path for one layer, or speculative decoding is off the table — there is no third option.
7. **The head, not the embedding, is the per-token cost.** `token_embd` is read
   by index (one row per token); `output.weight` is read in full, 0.67 GiB every
   token, and it is the largest single tensor in the file. Any per-token byte
   budget starts there.
