# H-4 — in-situ rates for IQ3_XXS, IQ2_S, IQ4_XS, Q4_K

Probe A2, 2026-10-23. Card `AMD Radeon RX 7900 XT`, 42 CU, PCI `0000:07:00.0`
(`HIP_VISIBLE_DEVICES=1`, headless). Wall **776.0 GB/s**. Scratch `~/a4/`.

## Question / hypothesis (from the ledger row A2)

The standing whole-file estimate is: 3.393 GiB of IQ3_S at 516.4 GB/s **plus 7.560 GiB of
everything else at 752 GB/s** → 56.1 tok/s, marked `estimated` in `RECORD.md` and annotated
"optimistic, assumes non-IQ3_S types at 752". The 752 figure came from a clean-4-bit
dequant-GEMV, not from any of these four layouts. H-4 asks two things per type:

1. **Does the layout penalise the read?** (load floor, byte-complete checksum)
2. **What does the dequant cost?** (dequant-dot rate, gated against an independent fp64 reference)

Hypothesis under test: the four types stream at 752 GB/s, so the estimate holds.

**Answer: it does not hold.** The two types whose dequant could be gated run at 452–502 GB/s,
i.e. 60–67 % of 752. Re-derived with measurements, the file decodes in 21.24 ms/token =
**47.1 tok/s**, not 56.0 — the standing estimate overstates by 19 %.

## Configuration (card, clocks, GRIDMUL, footprints, manifests, pass counts)

- **Clocks pinned** `power_dpm_force_performance_level=high` on
  `/sys/class/drm/card0/device` (= `0000:07:00.0`) before the first run; **restored to `auto`**
  after the last (`cat` prints `auto`).
- **Never touched** HIP device 0 / PCI `03:00.0` (display). Every log prints
  `device: AMD Radeon RX 7900 XT, 42 CU, PCI 0000:07:00.0 (HIP_VISIBLE_DEVICES=1)`.
- **`GRIDMUL=8 BLK=256` → `grid=336 x 256 = 86016 threads (2688 warps)`** in all 12 logs.
- `rp=4` (4 rotated passes) for every type; kernel time 3.5–9 ms per timed region, above the
  ~3 ms unmeasurability floor. 5 launches per row, median of the middle 3 reported.
- Harness `~/a4/pertype.cpp` derived from `~/e1/iq3s_valid.cpp`: the block stride is now a
  **runtime** value, and the read kernel hashes **every byte of the block exactly once**
  (8 B per 32-weight group over bytes 0–63, then bytes `[64, stride)` as 2-byte words spread
  over the 8 groups) instead of a few named fields.
- Manifests `~/a4/mkmanifest2.py` = `~/e1/mkmanifest.py` with a type filter and a per-type
  stride. Called once per type; **each call printed `structural check: 387 tensors with a
  documented layout, 0 mismatches`**, and the harness re-checks `stride × nblk × rows ==
  manifest bytes` for every row it loads (`LAYOUT FAIL` would abort).

| type | tensors in manifest | shape | rows | footprint | REPL | rp |
|---|---|---:|---:|---:|---:|---:|
| Q4_K | 1 — `output.weight` | 5120×248320 | 248 320 | **1.3321 GiB** | 2 | 4 |
| IQ4_XS | 25 — `blk.*.ffn_{up,down,gate}` etc. | 5120×17408 | 17 408 | **1.1024 GiB** | 1 | 4 |
| IQ3_XXS | 39 — `blk.*.ffn_{up,gate}` etc. | 5120×17408 | 17 408 | **1.2393 GiB** | 1 | 4 |
| IQ2_S | 1 — `token_embd.weight` | 5120×248320 | 248 320 | **1.1378 GiB** | 3 | 4 |

`REPL` is the harness's documented buffer-replication knob (the same bytes copied N times on
the device) used only where a single (ne0,ne1) shape group was smaller than 1 GiB; it makes
the footprint large enough that nothing can be L2-resident, and the checksum is multiplied by
it exactly.

**Load granularity, stated once:** all four Phase-1 rows use 2-byte accesses, i.e. the same
`load8`-class scheme E1 used for IQ3_S (110 B stride, also only 2-aligned), so no type is
credited or penalised for its stride alignment. An aligned `uint4` stream over the *same
bytes* (`wall_flat`) is reported beside each row as the alignment-free control.

## Phase 1 — load floor

Median of 3 runs. `read` = real block addressing, one lane per 32-weight group, every byte
touched once; `wall_flat` = aligned `uint4` stream of the same bytes.

| type | B / 256 w | checksum | `wall_flat` | **`read`** | % wall | read / flat |
|---|---:|---|---:|---:|---:|---:|
| Q4_K | 144 | match, VALID | 676.6 | **659.6** | **85.0 %** | 97.5 % |
| IQ4_XS | 136 | match, VALID | 657.4 | **637.1** | **82.1 %** | 96.9 % |
| IQ3_XXS | 98 | match, VALID | 668.4 | **643.6** | **82.9 %** | 96.3 % |
| IQ2_S | 82 | match, VALID | 659.4 | **656.6** | **84.6 %** | 99.6 % |

All 12 read rows (4 types × 3 runs) `match` and are ≤ 776 GB/s. Run-to-run spread is ≤ 1.3 % on the read rows and ≤ 1.7 % on the two gated dot rows.

**Reading of the table:** block-addressed reading costs **0.4–3.7 %** of the flat stream at
these strides — 82 B, 98 B, 136 B and 144 B, i.e. two of them not even 4-byte aligned. The
layout does **not** penalise the read for any of the four types, which extends E1's IQ3_S
result (92.5 % of wall, later 522.7-based re-runs) to the whole of the non-IQ3_S bytes. The
flat controls themselves sit at 84.7–88.6 % of the 776 wall at ~1.1–1.3 GiB, matching E1's
own 668.5 GB/s flat control at 1.07 GiB — so the missing ~12 % of the wall is a property of
this footprint size, not of any quant type.

## Phase 2 — dequant-dot

Tolerance **stated before the run: worst per-row relative error ≤ 2.0e-03** against an
independent fp64 CPU reference in the same binary (decode + dot in `double`, from the GGUF
bytes; the kernel accumulates in `int32`/`fp32`). Same 1.1–1.3 GiB footprint, `rp=4`.

| type | GB/s | % wall | dot / read | fp64 worst rel err | rows over tol | checksum | verdict |
|---|---:|---:|---:|---:|---:|---|---|
| **IQ4_XS** | **502.1** | 64.7 % | 78.8 % | **2.239e-06** | 0 / 32 | match | **measured** |
| **Q4_K** | **452.2** | 58.3 % | 68.6 % | **4.938e-06** | 0 / 32 | match | **measured** (kernel-limited, see below) |
| IQ3_XXS | — | — | — | 1.426e+00 | 32 / 32 | MISMATCH | **unmeasured** |
| IQ2_S | — | — | — | — | — | — | **unmeasured** |

Both measured rows are `match` and ≤ 776 GB/s in all three runs; the IQ4_XS row reproduced to
0.06 % across runs (501.8 / 502.1 / 502.1) and Q4_K to 1.7 % (457.2 / 452.2 / 449.7).

What the kernels are, in documented terms (03c + 15-quant-kernels):

- **IQ4_XS** — `d`(f16) + `scales_h`(2) + `scales_l`(4) + `qs`(128); `w = d·(sc6−32)·T16[q]`,
  one **signed** 6-bit scale per 32, no min. Table synthesised in registers with
  `v_perm_b32` (2 perms + mask/select per 4 codes), 8 `v_dot4_i32_i8` per 32 weights.
  `v_perm_b32`'s selector convention was **measured on this card**, not assumed
  (`~/a4/permtest.cpp` → `~/a4/permtest.log`: `sel[1:0]` picks the byte, `sel[2]` picks the
  word with `sel[2]==0` reading SRC1), and the gather is re-verified in-binary on every run
  against a scalar table read: `perm self-test: 0 of 64 gathered bytes disagree`.
- **Q4_K** — `d`(f16) + `dmin`(f16) + `scales`(12) + `qs`(128); `w = d·sc_i·q − dmin·m_i`,
  8 sub-blocks of 32. The 4-bit plane is not sequential: 03c's per-lane shape ("2× 4 B,
  16 B apart per 16 w") with 128 B / 256 w fixes the tiling to four 32-byte bands, each band
  holding two 16-weight pieces 16 B apart (`qs[32Q+4r]` and `qs[32Q+16+4r]`), sub-block
  `s = j/2`. Two accumulators, because `−dmin·m` multiplies `Σx`; the extra
  `v_dot4` against `0x01010101` is the documented second accumulator, so 16 `dp4a` per
  32 weights.
- The **6-bit scale/min packing** for Q4_K was selected by a data test, not by memory of any
  implementation: `w = d·sc·q − dmin·m` with min/max taken from the block gives
  `2·dmin·m = 15·d·sc`, i.e. `r = dmin·m/(d·sc) ≈ 7.5`. Four candidate packings were scored on
  real sub-blocks (`~/a4/layout_probe2.log`): the selected one gives median r = **7.42**,
  IQR/median 0.247, 99.3 % of sub-blocks in [3.75, 15], 0 % zero fields; the alternatives give
  IQR/median 0.450 / 0.898 / 0.941 and 91.8 / 64.7 / 62.8 % in band. The same test located the
  fp16 fields: offset 0 is the only offset with `frac_finite = 1.000`, median |v| 7.68e-05 and
  positive lag-1 log correlation (+0.226).
- **Which nibble is which weight** is a convention, as E1 recorded for IQ3_S (RESULTS.md
  caveat 4): it permutes the terms of the dot, not the instruction count, and the fp64
  reference is built from the same mapping. The full decode reproduces sane model statistics —
  mean |w| 1.02–1.25e-02, rms 1.26–1.56e-02, row mean ≈ 1e-04 — for both Q4_K and IQ4_XS, and
  a pure-Python decode (`~/a4/dotcheck.py`) reproduces the C++ reference to 7 digits.

### Why Q4_K's 452.2 is a floor for this kernel, not the format's corner

Phase 3 shows the Q4_K body at **344 instruction words per 32 weights**, 1.8× IQ3_S's 193.
The cause is mine, and it is in the census: `q4k_scmin` selects between the `j<4` and `j>=4`
6-bit unpack forms with a **runtime** branch on the sub-block index, inside the hot loop, and
the min term doubles the `dp4a` count. A kernel that unrolls the 8 sub-blocks so the unpack is
constant-folded would issue substantially fewer words for the same bytes. So: **the Q4_K
reading floor (659.6, 85.0 %) is a statement about the format; the 452.2 dot rate is a
statement about this kernel.** It is reported as measured because it is correctly gated and
reproducible, but it must not be read as Q4_K's best possible corner.

### Why IQ3_XXS is unmeasured

The accounting is exact and unique — 98 B = `d`(2) + 64 B of 8-bit grid indices (8 per
32 weights, 4 weights per 256-entry entry) + 32 B of sign bits, which is the only split of
96 bytes that satisfies "8 grid loads per 32 weights" and 1 sign bit per weight, and it
matches the doc's "2 B only" scale overhead (no per-group scale: there is no byte left for
one). `d`@0 is confirmed by the fp16 signature (the only offset with `frac_finite = 1.000`).
An 8-bit code width is required by the data: a 4-bit reading puts the weights at
mean |w| 6.1e-04, 20× below the 1.1–1.25e-02 the other three types decode to.

The kernel implements exactly that, and it **fails both gates**: fp64 worst relative error
**1.426e+00** on 32/32 rows, and the checksum MISMATCHes. A byte-level dump shows the grid
words, the sign nibbles and 7 of the 8 per-group integer dots agreeing with the reference and
the divergence starting at group 4; that is where it stands. The discarded rows ran at
581.5–592.3 GB/s — *above* IQ3_S's gated 516.4 — which is the signature of a kernel doing less
work than it counts. **No rate is reported for IQ3_XXS.** Its load floor stands.

### Why IQ2_S is unmeasured

Two independent reasons, either sufficient:

1. The documentation does not close. `03c` gives IQ2_S as 82 B with "8 B qs + 1 B qh per
   group", "signs in separate 32 B" and 10 B of scale overhead. But `d`(2) + `qs`(64) +
   `qh`(8) + `scales`(8) = **82 exactly**, leaving no room for a 32 B sign plane. One of those
   statements is wrong and the file does not say which.
2. The data gives no field order to break the tie. T1 scans **every** byte offset 0–80: no
   offset reaches `frac_finite = 1.000` with a weight-scale magnitude. The best offsets by
   lag-1 smoothness sit at median |v| 0.16–0.48 (`off 77/79/78/73/74`), three to four orders of
   magnitude too large for a per-block scale, and the small-magnitude offsets (`66`, `72`,
   median 7.6e-04 / 1.0e-03) have **no** lag-1 correlation. For comparison, Q4_K/IQ4_XS/IQ3_XXS
   all show a clean 1.000-finite, 1e-5..1e-4, smooth signature at exactly one offset.

So the layout is not identifiable from the documentation plus the bytes, and per the brief I
stop: **load floor reported, dot rate unmeasured, no number invented.** The 656.6 GB/s load
floor is still useful — it says the bytes are not the problem for IQ2_S either.

## Phase 3 — census

`llvm-objdump`-class assembly from `hipcc --offload-arch=gfx1100 -O3 -S --cuda-device-only`
(`~/a4/pertype_dev.s`), hot loop delimited by its single backward branch, as H-2 did. One
`v_dual_*` line is one 8-byte VOPD word carrying two ALU operations: `words` counts lines,
`ops` adds one for every dual line.

| kernel | unit (w/lane) | words | ops | `dp4a` | mem loads | `v_perm` | VALU | VGPRs | **words / 32 w** |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `k_read` (load floor) | 32 | 32 | 32 | 0 | 1 (vectorised) | 0 | 18 | 28 | 32 |
| `k_iq4xs` | 32 | 146 | 149 | 8 | 13 | 16 | 80 | 43 | **146** |
| `k_iq3xxs` | 32 | 155 | 155 | 8 | 27 | 0 | 66 | 35 | **155** |
| `k_q4k` | 16 | 172 | 181 | 8 | 12 | 0 | 96 | 37 | **344** |
| *IQ3_S (H-2, reference)* | 32 | — | — | 8 | — | — | — | — | **193** |

Consequences, in the order the numbers put them:

- **IQ4_XS's 146 words buys 78.8 % of its own read floor.** Its 16-entry table is gathered in
  registers with 16 `v_perm_b32` — no data-dependent load in the critical path.
- **IQ3_XXS's 27 memory operations per 32 weights** are the documented 8 grid loads plus the
  8 sign-mask loads that replaced the SWAR mask; it is the most load-heavy shape of the four
  and would be the one to attack with pre-shred signs.
- **Q4_K's 344 words** are the reason its dot rate is the lowest of the two measured, and they
  are dominated by the runtime-branching 6-bit unpack, not by the `dp4a` count (8 per
  32 weights, the same as the others).
- An **issue-occupancy percentage** (the 48.6 % H-2 quotes for IQ3_S) is *not* reported here:
  it needs the perfcounter work of H-2, and fabricating it from VGPR counts would be arithmetic
  pretending to be a measurement. VGPRs are given so the figure can be computed by whoever
  runs that sweep.

## What this changes

The whole-file estimate must be re-derived, and the direction is down:

| scenario | ms / token | tok/s |
|---|---:|---:|
| standing estimate (everything but IQ3_S at 752) | 17.85 | 56.0 |
| **re-derived: IQ3_S 516.4, IQ4_XS 502.1, Q4_K 452.2 measured; the rest still at 752** | **21.24** | **47.1** |
| optimistic bound: Q4_K at its own read floor (659.6) | 20.14 | 49.6 |

- **The 752 GB/s assumption is 30–40 % too high** for the two types that could be measured:
  IQ4_XS runs at 66.8 % of 752, Q4_K at 60.1 %. The estimate overstates decode by **19 %**
  (56.0 → 47.1 tok/s), and the gap is not in the bytes — all four load floors are 82–85 % of
  the wall — it is entirely in the dequant.
- **47.1 tok/s is still an upper bound.** IQ3_XXS (1.933 GiB, 17.6 % of the file) and IQ2_S
  (0.745 GiB, 6.8 %) still ride on the 752 assumption inside that number, i.e. **24.4 % of the
  file is still unmeasured at the dot**. IQ3_XXS is the larger and the more load-heavy of the
  two; closing it is the single biggest remaining error term in the estimate.
- **The dequant, not the layout, is the budget.** For every type the read is within 3.7 % of the
  aligned stream, and the dequant then costs a further 21–31 % of what was read. Optimising
  strides, alignment or addressing cannot recover any of it.
- **Q4_K is the outlier to re-run, not to believe.** 452.2 with 344 words/32 w says the 6-bit
  unpack is worth 1.8× IQ3_S's instruction count *as I wrote it*. Before this row enters a
  plan, it needs the sub-block-unrolled kernel; the 3.8 ms/token it costs at 452.2 would fall
  to 2.65 ms at its own read floor.

## Compliance

- **llama.cpp excluded**: not cloned, not built, not installed, no source read, no derived
  code. Layout semantics come from `docs/research/2026-10-22/03c-gguf-quant-layouts.md`
  (field sizes), `docs/research/15-quant-kernels.md` (the affine laws), and **tests on the GGUF
  bytes themselves** (`~/a4/layout_probe.py`, `~/a4/layout_probe2.log`). The two codebooks are
  **placeholders of the documented shape** (256×u32 grid of 4 int8, 16 int8 values), generated
  by a fixed xorshift, because their contents are in neither the file nor our docs; as in E1
  (RESULTS.md caveat 2) no rate depends on them — every row's cost is loads + ALU + bytes, and
  the fp64 reference consumes the same table.
- **The gate**: every reported row carries a data-dependent checksum replayed on the host from
  the GGUF bytes (`match`), **every gated row is ≤ 776 GB/s**, and a row above the wall would
  have been discarded automatically. `grid=336 x 256` appears in all 12 sweep logs.
- **Repo unmodified** — no file in the repository was written by this probe except this report.
- **Clocks restored**: `power_dpm_force_performance_level` on `card0/device` (= PCI `07:00.0`)
  was `high` for every run and is `auto` again (verified).
- **Display card untouched**: `HIP_VISIBLE_DEVICES=1` throughout; every log prints
  `PCI 0000:07:00.0`.
- A type that could not be implemented is reported **unmeasured with the failing gate as the
  evidence**, never as a plausible number: IQ3_XXS (fp64 1.426e+00, checksum mismatch) and
  IQ2_S (layout not identifiable).
