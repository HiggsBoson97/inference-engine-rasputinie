# H-5 — drafter selection: shipped MTP head vs DFlash2

Probe: DISCOVERY · read-only · no GPU job · 2026-10-23
Tree: `engine/` = vendored sglang `d0a7565` (`engine/UPSTREAM.md:5`), 11 063 files, 4 636 of them Python.
Model: `ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF` IQ3_S, 11 771 546 784 B trunk, 12 120 016 960 B `-mtp` variant.

**Evidence labels used throughout:** `[measured]` someone ran it on hardware ·
`[published]` the model card, a paper or the vendored code claims it · `[derived]` my arithmetic
from stated inputs. Nothing in §C is measured on this box.

## Question

> Which drafter — the shipped MTP head or DFlash2 — and what does each cost per verification
> step here? (ledger row H-5, `docs/agents/production/hypothesis-ledger.md:17`)

The ledger's hypothesis, quoted so the report can agree or disagree with a specific sentence:

> DFlash2's block-diffusion draft (one pass per block) beats MTP's autoregressive draft at
> concurrency 1, but its ~4 GB BF16 footprint costs the KV budget ~2.5 of the ~4.1 concurrent-32K
> sessions per card that the MTP head leaves, so it must be quantised to be deployable.

**Verdict: confirmed on the mechanism, wrong on the magnitudes.** DFlash2's draft *is* flat-cost
and MTP's is not — by a wider margin than the H200 card shows, because on this box every draft
token re-reads a 0.666 GiB LM head. The session arithmetic is off in both terms: the MTP head
leaves **6.0** concurrent 32K sessions per card, not 4.1, and BF16 DFlash2 costs **1.26** of
them, not 2.5 (§C.3). The conclusion — quantise the drafter or lose sessions — survives, and is
weaker than the ledger thought, not stronger.

- `srt/arg_groups/speculative_hook.py:855-860` — and the engine already resolves this for us:
  `# FlashInfer is CUDA-only; fall back to triton on XPU and ROCm.` →

  `cfg.device.startswith("cuda") or cfg.device == "npu" or cfg.device == "xpu"`. ROCm reports

one `triton` flag away, and the one real unknown is whether Triton-on-gfx1100 compiles and runs
the non-causal, sliding-window-2048, 32/8-head-128 attention at block width 8 at any sane speed.
That is a kernel question, not a porting question.**

### A.3 The MTP path is a different shape of problem

MTP is not its own algorithm. It runs as `--speculative-algorithm EAGLE` against a **separate
draft checkpoint**:

- `srt/models/qwen3_5_mtp.py:94` — `Qwen3_5ForCausalLMMTP`, one decoder layer plus `eh_proj`
  and three norms; `set_lm_head_from_target` (`:182`) confirms it borrows the target's head
  rather than shipping one.
- The loader picks that class by **rewriting the draft checkpoint's own config**:
  `configs/model_config.py:1036-1065` (`is_draft_model` → `architectures[0] = ...MTP`,
  `num_nextn_predict_layers = 1`). The MTP architecture is inferred *from a config file that
  travels with the draft*, not from the target.
- The EAGLE handler wants `--speculative-draft-model-path`; the "draft is bundled inside the
  target checkpoint" convention exists only for DSPARK, keyed on `dspark_*` keys in the target's
  HF config (`arg_groups/speculative_hook.py:604-609`, `speculative/dspark_components/dspark_config.py:158-170`).

Our MTP head is 15 tensors named `blk.64.*` inside `Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp.gguf`
(`docs/plan/TENSOR-INVENTORY.md:518-534`). There is no `config.json`, no `architectures[0]`, and
the GGUF loader name-maps through `gguf.get_tensor_name_map(arch, num_layers)`
(`model_loader/loader.py:3046-3097`), which has no concept of a 65th `nextn` layer. **Neither
drafter is a drop-in for us, but they are drop-in *differently*:** DFlash2 is a standard
checkpoint in a standard layout that the tree already loads (`DFlash2DraftModel` is registered in
`models/dflash.py:1224`); MTP is a non-standard artifact that has to be exported to a directory
with a fabricated config before any engine — vendored or bespoke — can see it.

Second MTP-specific cost, invisible until you read the code: the draft shares the target's
`output.weight`, so **every draft step re-reads the full 0.666 GiB Q4_K head** (§C.1).

## B. What DFlash2 is

### B.1 Architecture, from the config and the card

`config.json` (`huggingface.co/z-lab/Qwen3.8-27B-DFlash2/raw/main/config.json`) `[published]`:

```
architectures: ["DFlash2DraftModel"]   num_hidden_layers: 5    hidden_size: 5120
intermediate_size: 17408               head_dim: 128           32 q / 8 kv heads
is_causal: false                       sliding_window: 2048    layer_types: 5 × sliding_attention
vocab_size: 248320                     num_target_layers: 64   dtype: bfloat16
dflash_config: block_size 8, conv_kernel_size 2, conv_group_size 16,
               selector_rank 256, selector_top_k 16, mask_token_id 248070,
               target_layer_ids [5, 19, 33, 47, 61]
```

- **2B params, BF16**: `safetensors` reports `{"BF16": 1924404480}`, total 1 924 404 480, storage
  3 849 104 785 B = **3.849 GB = 3.585 GiB** `[published]` (HF API, model `sha 50307d4`).
  Note the card's "2B params" is 1.92 B; the brief's "~4 GB" is right.
- **No embedding, no LM head** — neither tensor exists in the file. `models/dflash.py:1-3`
  ("Most drafts borrow the target embedding and LM head") and
  `dflash_worker_v2.py:1473` (`draft_model.lm_head = lm_head`). So the 3.849 GB is *all*
  drafter.
- **Two-tap dynamic convolutions**: `DFlashGroupedConv` (`models/dflash.py:504-560`),
  "Grouped dynamic depthwise K-tap convolution across one DFlash block… Each sublayer is wrapped:
  `prepare` convolves its input and returns the kernel for `finish` to convolve its output, both
  from one projection of the input" (`:507-510`). `conv_kernel_size: 2` is the "two-tap"; the
  purpose per the card is to stop the draft "decaying toward the end of the block".
- **Candidate-path selector**: `CandidateSelector` (`models/dflash.py:1102`), "Scores the K×K
  transitions between adjacent proposal slots, then walks them" (`:1103`). Two `[vocab, 256]`
  codebooks (`:1127-1133`) = 2 × 127 MB, replicated on every TP rank (`:1105-1107`) — 254 MB of
  the 3.849 GB is codebook, and it is read every block.

### B.2 The draft cost structure — the part that decides this

Per proposed block, **one** forward pass, not seven:

```
dflash_worker_v2.py:2672   draft_out = self.draft_model_runner.forward(forward_batch)
```

That single call is the only draft forward in the file. The block is built before it by filling
7 slots with `mask_token_id` and putting the last verified token in slot 0
(`dflash_worker_v2.py:2538-2539`: `block_ids.fill_(int(self._mask_token_id)); block_ids[:, 0].copy_(draft_input.bonus_tokens)`),
and the whole non-causal block is denoised at once (`is_causal: false`, all layers
`sliding_attention`). Then:

1. `candidate_topk` (`models/dflash.py:105-145`) projects the 7 predicted hidden states through
   **the target's LM head** and keeps the global top 16 per position.
2. `_selector_lattice` + `selector_walk_triton` score the 16×16 transitions and walk **one**
   path (`kernels/ops/speculative/dflash.py:251-297`), emitting 7 tokens plus a per-slot `q`.
3. One target verify pass accepts the longest matching prefix and appends the target's next token
   as a bonus, linearly — not a tree (`dflash_info.py:39`).

**So the draft's weight traffic is: drafter (once) + LM head (once, for 8 rows).** Not once per
token. That is the whole economic difference from MTP, whose head read is per step.

### B.3 What it needs from the target — the integration constraint

`target_layer_ids [5, 19, 33, 47, 61]` means the drafter consumes **five intermediate hidden
states of the target**, fused by `fc` (`[5120, 25600]`, 262 MB BF16). This is not a logits-only
bolt-on: the target's layer loop must export activations at five fixed layer indices, and the
selector then needs the target's LM head as a *readable matrix*. The vendored path enforces the
latter bluntly:

```
models/dflash.py:120-126
    if not use_quant_head and not is_dense_head_weight(weight):
        raise RuntimeError(
            "DFlash candidate top-k requires a dense FP16/BF16/FP32 target lm_head "
            "or a supported lm_head.quant_method.")
```

with `is_dense_head_weight` = "weight.dtype in _DENSE_HEAD_DTYPES"
(`speculative/dflash_utils.py:820-824`). Our head is Q4_K, 0.666 GiB. **In sglang this would force
a dense BF16 copy of the head — 248 320 × 5120 × 2 = 2.54 GB `[derived]` — which would be a larger
cost than the drafter itself.** In our own engine it does not: we already read `output.weight` as
a Q4_K GEMV, so the constraint is an sglang loader artefact, not a property of DFlash2. Worth
stating plainly because it is the kind of thing that gets discovered late and kills a slice.

### B.4 Losslessness

The card states it without qualification: "Decoding is lossless: greedy output matches the target
model exactly, and sampling preserves its distribution" `[published]`
(`huggingface.co/z-lab/Qwen3.8-27B-DFlash2`). Structurally this is the standard speculative
argument applied to a block: the target verifies every proposed token, so the *output* cannot
differ from the target's own — acceptance changes speed, never text. The one thing that can break
it is the selector's sampling path, which is why the walk carries per-slot `q` probabilities and a
rejection-sampling accept (`dflash_worker_v2.py:1508` `_selector_sampling_accept`). For a greedy
deployment the claim reduces to "verify the prefix exactly", which is testable and cheap to test.

### C.3 VRAM per card and concurrent 32K sessions

Card = 19.98 GiB = 21.45 GB. Trunk at TP=2 = 5.886 GB/card = **5.48 GiB** (matches
`docs/research/2026-10-22/04-kv-cache.md:47`), leaving 14.50 GiB raw. The project's planning
figure for the KV pool is **7 GiB/card** (`04-kv-cache.md:68`) — the other ~7.5 GiB is
activations, graph pools and sampler buffers. Per 32K session: **1.00 GiB KV + 0.074 GiB GDN
state = 1.074 GiB/card at bf16**, 0.604 GiB at q8_0 (`04-kv-cache.md:70-73`); the 159 MB state is
7 % of a session's total footprint because it is shared with 2 GiB of KV across both cards.

| drafter | drafter/card | drafter KV/seq | sessions bf16 KV | sessions q8 KV |
|---|---:|---:|---:|---:|
| none | 0 | 0 | **6.52** | 11.59 |
| MTP 7-step | 0.162 GiB | 0.0625 GiB (1 extra full-attn layer, 4 KiB/token, TP=2) | **6.02** | 10.26 |
| DFlash2 BF16 | 1.792 GiB | 0.020 GiB (2048-token window × 20 KiB/token, TP=2) | **4.76** | 8.35 |
| DFlash2 4.5 bpw | 0.504 GiB | 0.020 GiB | **5.94** | 10.42 |

Read that as: **BF16 DFlash2 costs 1.26 of 6.02 sessions (−21 %); at 4.5 bpw it costs 0.08
(−1.3 %).** The ledger's "~2.5 of ~4.1" is off in both terms because it assumed a ~4.7 GiB pool;
at the project's own 7 GiB figure the absolute session count is higher and the drafter's share is
smaller. The direction is unchanged: BF16 is a real capacity cost, quantised is nearly free.

One open sizing question I could not close by reading: the draft KV *cell* is computed per token
without a window clamp — `dflash_draft_cell_size_per_token` is
`num_kv_heads × (head_dim + v_head_dim) × layers × dtype` (`speculative/dflash_utils.py:121-133`),
which charges 10 KiB/token/card; at 32K that is 320 MiB/seq, not 20 MiB. Whether the pool is
allocated over the 2048-token window or over the full context is decided elsewhere in the memory
pool and I did not trace it. **If it is charged per token, DFlash2's draft KV is 0.31 GiB/seq and
the session count drops to 4.7 (bf16) — the same as the BF16 drafter weights.** That is a
measurement, not a reading, and it belongs in the A3 probe.

---

## D. Conditions for DFlash2 to win here

Each is falsifiable, and each names the measurement that settles it. In dependency order — the
first two are the ones that can kill the idea before any integration work.

| # | condition | threshold | measurement |
|---|---|---|---|
| D1 | **Triton-on-gfx1100 runs the draft attention at all** | compiles and produces a finite block-8 draft, non-causal, window 2048, 32/8 heads @ head_dim 128 | one forward of `DFlash2DraftModel` at bs=1, block 8, on a synthetic 32K prefix; assert finite logits and match the 7 candidate ids against a CPU reference |
| D2 | **The selector's top-k fallback is not the throughput cliff the code warns about** | selector + `_selector_lattice` + `candidate_topk` ≤ **1.5 ms** per block at bs=1 | CUDA-event timing of the three calls in isolation; the byte count is 6.9 MB so anything above ~0.1 ms is kernel latency |
| D3 | **The drafter's forward achieves target-like bandwidth** | ≥ **400 GB/s** effective on the 1.083 GB 4.5 bpw drafter (i.e. ≤ 4.5 ms) | one timed draft forward at bs=1, block 8, weights resident; compare against the same-size GEMV microbenchmark |
| D4 | **Acceptance transfers to this finetune** | **A ≥ 3.0** at block 8, greedy, on 6 coding prompts of ≥ 512 tokens | the A3 probe: accepted tokens ÷ verification steps, logged per request. Below 3.0 DFlash2 ≈ MTP-7 and the integration is not worth it |
| D5 | **Acceptance survives 4.5 bpw quantisation** | **≥ 90 %** of the BF16 acceptance | same prompts, same seed, drafter quantised; the only experiment that justifies the 1.08 GB footprint |
| D6 | **The five aux hidden states are cheap to expose** | ≤ 1 % of step time, ≤ 410 KB/step at bs=1 | instrument the target's layer loop at layers 5/19/33/47/61; measure the copy, not the guess |
| D7 | **Draft KV is window-clamped, not context-charged** | ≤ 32 MiB/seq at 32K | read the allocated pool size out of the engine after a 32K session, or instrument the allocator |
| D8 | **End-to-end beats MTP by a margin worth the work** | ≥ **1.25×** MTP's tok/s at the same acceptance protocol | one server, both drafters, same prompts: the go/no-go |

The falsifier for the whole lane: **if D1 or D4 fails, DFlash2 is dead here** and no kernel work
recovers it — D1 because the path cannot run, D4 because the drafter was trained on Qwen3.8's
hidden states and this target is four rounds of SFT + RLOO downstream of them. MTP has the same
D4 exposure and is the cheaper way to learn it: it needs no new loader and no new architecture,
and it exercises the plumbing DFlash2 also needs (multi-token verify against 48 GDN layers, state
rollback, graph capture at a non-1 draft width).

---

## Recommendation

**Build MTP first, DFlash2 second — but design the verify path for DFlash2's block from day one,
because the cost model says DFlash2 is the better drafter and only its integration risk is worse.**
On this box MTP's autoregressive draft costs 1.064 GB per draft token (0.325 GiB layer + 0.666 GiB
head re-read) → 14.3 ms per verification step at 7 tokens, 65.6 % of a target sweep, for 139 tok/s
at published acceptance. DFlash2's flat block costs 1.798 GB at 4.5 bpw → 3.45 ms, 15.8 % of a
sweep, for 216 tok/s; even at BF16 it is cheaper than MTP-7 (4.564 GB, 8.76 ms, 179 tok/s). It
costs 1.26 of 6.02 concurrent 32K sessions at BF16 and 0.08 at 4.5 bpw, and it is legally
unencumbered (MIT code, Apache-2.0 weights). It is also, per §A.2, already in the tree as Triton
with an explicit ROCm fallback — nothing on the path is CUDA-only by import.

What would change this: **D1** (Triton cannot run the non-causal draft attention on gfx1100 at
usable speed) makes DFlash2 an implementation project rather than an integration one and MTP wins
by default; **D4** (acceptance < 3.0 on our prompts) kills both drafters and the answer becomes
"fix the weight path before speculating at all" — at 521 GB/s the unspeculated ceiling is 45.9
tok/s and no drafter fixes a kernel that is 33 % off its own memory wall. The one thing I would
not do is choose on the card's 3.43× vs 2.59×: that ratio was measured with FlashAttention 3 on an
H200, and on this box the same byte arithmetic produces 3.89× vs 3.03× for the *same* two drafters
— a different number, from the same inputs, with none of the same kernels.
