## Question

Can the vendored sglang serve `Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf` on gfx1100, at what rate, and **which
dequantisation path does it take on ROCm** — `ggml_mul_mat_vec_a8` (MMVQ), `ggml_mul_mat_a8` (MMQ), or
`dequantize_gguf_weight → ggml_dequantize → bf16 matmul`?

Hypothesis under test (from the brief): *MMQ is CUDA-only, therefore the dequant fallback at
`gguf.py:223` is what runs, so the first optimisation is "replace dequant+GEMM with a fused dp4a GEMV".*

## The dequant path on ROCm

**The engine's own statement, verbatim** (`~/b1/logs/14_quantlog.log`, constructed `GGUFConfig()` on the
ROCm stack):

```
WARNING (engine, GGUFConfig.__init__): Only CUDA and MUSA support GGUF quantization currently.
GGUFConfig.get_name(): gguf
GGUFConfig.repr: GGUFConfig()
IQ3_S membership -> MMVQ: True | MMQ: False | DEQUANT: True
```

**The import block decides it** — `engine/python/sglang/srt/layers/quantization/gguf.py:55-73`:

```python
if _is_cuda:
    from sgl_kernel import moe_sum
    from sgl_kernel.quantization import (
        ggml_dequantize, ggml_moe_a8, ggml_moe_a8_vec,
        ggml_mul_mat_a8, ggml_mul_mat_vec_a8,
    )
    ...
elif _is_musa:
    from sgl_kernel import gelu_and_mul, moe_sum, silu_and_mul
    from sgl_kernel.quantization import ( ... same five ... )
elif _is_npu:
    from gguf import dequantize as gguf_dequantize
else:
    if not _is_hip:
        warnings.warn(f"Only CUDA, MUSA and NPU support GGUF quantization currently.")
```

On this host `_is_cuda` is **False** — `is_cuda()` is `torch.cuda.is_available() and torch.version.cuda is
not None` (`srt/utils/common.py:158-159`) and `torch.version.cuda` is `None`; `_is_hip` is **True**
(`common.py:141-142`, `torch.version.hip is not None`). So **no `ggml_*` name exists in the module
namespace at all**, and the `else` branch deliberately stays silent on HIP.

**The branch order is not what the brief assumed.** `fused_mul_mat_gguf` (`gguf.py:213-238`) tests MMVQ
*before* MMQ and *before* the dequant fallback:

```python
if qweight_type in UNQUANTIZED_TYPES:            return x @ qweight.T
if x.shape[0] <= mmvq_safe and qweight_type in MMVQ_QUANT_TYPES:
                                                  y = ggml_mul_mat_vec_a8(...)   # 1. MMVQ
elif qweight_type in MMQ_QUANT_TYPES:             y = ggml_mul_mat_a8(...)       # 2. MMQ
elif qweight_type in DEQUANT_TYPES:               weight = dequantize_gguf_weight(...); y = x @ weight.T   # 3. dequant
```
with `mmvq_safe = 8 if qweight.shape[0] > 5120 else 16` for I-Matrix types (`gguf.py:208-211`).
IQ3_S is in `MMVQ_QUANT_TYPES` and in `DEQUANT_TYPES`, but **not** in `MMQ_QUANT_TYPES`.

**Measured dispatch, not inferred** (`~/b1/logs/11_branch_table.log`; the three kernels were replaced by
recording stubs *in memory* — `engine/` untouched — so the real selector ran):

```
case                        out   type  branch
--------------------------------------------------------------
decode   1 tok             7168  IQ3_S  ggml_mul_mat_vec_a8 [MMVQ]
decode   1 tok out=1024    1024  IQ3_S  ggml_mul_mat_vec_a8 [MMVQ]
decode   1 tok Q4_K        7168   Q4_K  ggml_mul_mat_vec_a8 [MMVQ]
verify   8 tok             7168  IQ3_S  ggml_mul_mat_vec_a8 [MMVQ]
verify   9 tok             7168  IQ3_S  dequantize_gguf_weight -> ggml_dequantize -> x @ w.T [DEQUANT+BF16 GEMM]
prefill 32 tok             7168  IQ3_S  dequantize_gguf_weight -> ggml_dequantize -> x @ w.T [DEQUANT+BF16 GEMM]
prefill 512 tok            7168  IQ3_S  dequantize_gguf_weight -> ggml_dequantize -> x @ w.T [DEQUANT+BF16 GEMM]
prefill 32 tok Q4_K        7168   Q4_K  ggml_mul_mat_a8 [MMQ]
```

**So: batch-1 decode takes MMVQ, not the dequant fallback.** The dequant → bf16 GEMM path appears only at
≥ 9 tokens (I-Matrix, `out > 5120`) — i.e. prefill and speculative verify. The brief's premise holds for
prefill only.

**And none of them can run here.** `ggml_dequantize.__module__` resolves to
`sgl_kernel.quantization.gguf` — but that is only the Python *wrapper*. The compiled operator is absent:

```
torch.ops.sgl_kernel.ggml_mul_mat_vec_a8
  -> AttributeError: '_OpNamespace' 'sgl_kernel' object has no attribute 'ggml_mul_mat_vec_a8'
ggml/quant ops registered in dispatcher: 0
total sgl_kernel ops: 47          (all_reduce_reg, moe_align_block_size, rotary_embedding,
                                   silu_and_mul, topk_softmax, transfer_kv_*, ...)
nm -C common_ops...so | grep -c ggml  ->  0
```

The cause is measured, not guessed — `python/sglang/kernels/aot/setup_rocm.py` compiles **10 `.cu`
sources** and `csrc/quantization/gguf/gguf_kernel.cu` is **not among them** (it *is* listed by
`setup_musa.py:94` and `setup_sail.py:211`). The ROCm wheel was built without the GGUF kernel family.

## Where the baseline sits

Nothing sits on the wall yet; only the arithmetic target is knowable, and it is **derived, not measured**:

| | ms/token | tok/s |
|---|---|---|
| 776 GB/s wall, 11.77 GB of weights read once per token | 15.17 | 65.9 |
| 521 GB/s (our measured fused dp4a GEMV) | 22.59 | 44.3 |

There is no gap to report against 521 GB/s, because there is no engine number to compare. What the probe
does establish is that **the engine's batch-1 decode path is already a fused GEMV** — MMVQ, selected at
`x.shape[0] <= 8` — so the project's fused-GEMV work is not a novel algorithm to introduce but a
**kernel to make available**: `vecdotq.cuh` in the vendored tree already contains the quantised dot
product in 2,037 lines with 45 `__dp4a` sites, and gfx1100 implements `__dp4a` natively.

## The first three things to change, ranked

1. **Guard the `aiter` import so the engine can start at all.**
   `python/sglang/srt/layers/quantization/quark/schemes/quark_w4a4_mxfp4.py:161-176` imports seven `aiter`
   symbols at module scope under `if _is_hip:`, for MXFP4 quark schemes this model never uses. Wrap in
   `try/except ImportError` with a lazy raise in the MXFP4 call sites.
   *Proof it worked:* `python -c "import sglang.srt.layers.quantization"` exits 0 and
   `python -m sglang.launch_server --help` prints. Today both exit 1.
   *Why first:* it blocks every other change, including H-11's, and it is a 3-line edit.

2. **Add the GGUF kernel family to the ROCm build: `csrc/quantization/gguf/gguf_kernel.cu` into
   `setup_rocm.py`, MMVQ first.** Build order MMVQ → dequantize → MMQ; skip MMQ (IQ types do not use it,
   and `mmq.cuh` is 881 lines of tile MMA with no `__dp4a`). The dp4a primitives are already there in
   `vecdotq.cuh`.
   *Proof it worked:* `torch._C._dispatch_get_all_op_names()` contains `sgl_kernel::ggml_mul_mat_vec_a8`,
   and a parity test on one random IQ3_S block against `gguf.quants.dequantize` gives max relative error
   < 1e-3. Both are one-liners against the existing `kernels/aot/tests/test_gguf.py` harness.

3. **Wire HIP into `gguf.py` and lift the gate — then take the baseline this probe could not.**
   Import the five `ggml_*` names when `_is_hip`, and add `"gguf"` to `rocm_supported_quantization`
   (`model_config.py:1977-1991`). Do these *after* (2), so the lifted gate leads to a working kernel
   instead of a `NameError`.
   *Proof it worked:* the launch line above reaches `Load weight` and the engine emits its
   `quant=gguf` config line, then TTFT and decode tok/s at batch 1, 32k context, with the output quoted.

Note which optimisation this re-ranks: the brief's first candidate — "replace dequant+GEMM with a fused
dp4a GEMV" — targets **prefill and verify only** (≥ 9 tokens). For the metric this project cares about
(decode tok/s at batch 1) the engine already dispatches to MMVQ; the honest first optimisation after the
three above is to **tune or replace the MMVQ kernel for gfx1100**, and the dequant path is a second,
separate target.
