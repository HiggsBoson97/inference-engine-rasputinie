# H-1 — is the IQ3_S dequant-GEMV VALU-issue-bound?

Probe: DISCOVERY · host `rasputin` · card PCI `07:00.0` (`HIP_VISIBLE_DEVICES=1`) · 2026-10-23
Scratch: `~/a1/` on the host. Orchestrator-authored after the dispatched probe was stopped;
the substitution is recorded in §2 and in the ledger.

## 1. Question / hypothesis (verbatim from the ledger)

> Is the IQ3_S dequant-GEMV at 516.4 GB/s limited by VALU issue slots?
> **Hypothesis:** on `k_full` at 1.0700 GiB, VALU issue-slot occupancy is ≥ 85 % of the
> SIMD32 slot rate, and `SQ_INST_CYCLES_VALU / SQ_INSTS_VALU ≥ 1.5`.
> **Settled by:** `rocprofv3` issue-slot occupancy, one counter readout.

## 2. The instrument does not exist on this host — measured, not assumed

The brief named `rocprofv3` on `SQ_INSTS_VALU` as the instrument. On this host that
counter is dead. Evidence, in order:

**a. A canary with a known instruction count.** `~/a1/canary.cu` is one wave, 100 000
iterations, one dependent `v_fma_f32` per iteration (`#pragma unroll 1`) — i.e. ~200 000
VALU instructions that cannot be optimised away. Under `rocprofv3`:

| counter | canary value | must be |
|---|---:|---|
| `SQ_WAVES` | 2 | 2 (64 threads / wave32) ✓ |
| `SQ_BUSY_CYCLES` | 2 304 427 | nonzero ✓ |
| `SQ_INSTS_VALU` | **0** | ~200 000 ✗ |

**b. Every candidate counter, one run each** (`~/a1/probe_counters.sh`, results in
`~/a1/ctest/`). Of 21 attempted, three collect:

| collects | reads zero on the canary |
|---|---|
| `SQ_BUSY_CYCLES`, `SQ_WAVES`, `Wavefronts` | `SQ_INSTS_VALU`, `SQ_INSTS_SALU`, `SQ_INSTS_SMEM`, `SQ_INSTS_LDS`, `SQ_INSTS_FLAT`, `SQ_INST_CYCLES_VALU`, `SQ_WAVE32_VALU`→rejected, `SQ_INSTS_WAVE32_VALU`, `SQ_WAVE32_INSTS`, `SQ_WAVE_CYCLES`, `GRBM_COUNT`, `GL2C_MC_RDREQ_sum`, `GL2C_EA_RDREQ_32B_sum`, `OccupancyPercent`, `ValuPipeIssueUtil`, `VALUBusy`, `VALUInsts`, `SIMD_UTILIZATION` |

`rocprofv3-avail pmc-check` is not a tiebreaker: it fails on the iGPU agent (`gfx1036`,
which supports no counters at all) for *every* counter, including ones that work.

**c. The real capture agrees.** `~/a1/cap1/` (three passes, eight counters, the real
kernel): 6 of 8 counters identically zero, `SQ_BUSY_CYCLES` and `SQ_WAVES` populated.
`~/a1/cap3/` repeats it with `--kernel-trace`: 12 dispatches of `k_full<0,0>` recorded,
same two counters alive.

**d. SQTT/ATT is also dead.** `--att` produced a code object and a `code.json` with
`"code": null` — no ISA mapping for gfx1100 in this build — so no per-instruction
issue/stall data either.

**Conclusion: `rocprofv3` on this host cannot read an instruction counter.** The A1
instrument as named in the handoff does not exist here. That is a rig gap and is recorded
as one; it is not a measurement of zero issue.

## 3. The test that replaced it (pre-registered before the run, recorded as a substitution)

The hypothesis is falsifiable without any counter, because it makes a behavioural
prediction: *if the kernel is issue-saturated, relieving memory pressure cannot make it
faster.*

**Test.** Run the **same kernel, same instruction mix, same checksum gate** twice:

- **DRAM arm** — 30 real tensors, 1.0700 GiB, `grid=336×256`, `rp=4` (the E1 config).
- **L2 arm** — 1 real tensor, 38 297 600 B (0.0357 GiB), which fits inside the 96 MB L2,
  so the weight stream is served from cache and DRAM is out of the picture. `rp=64` so the
  timed region is 2.45 GB of traffic ≈ 3.5 ms, above the ≥3 ms the wall report requires.

Second line of evidence: the emitted-ISA census (H-2), independently recounted here, gives
the instruction count per 32 weights, which converts a measured GB/s into an issue-slot
utilisation.

**Discarded, and why.** The first L2 attempt used `rp=4` (0.22 ms kernels) and produced
690.3 then 366.7 GB/s on identical input — the short-kernel regime trap 11 warns about.
Both runs are discarded; `~/a1/l2_run1.log`, `l2_run2.log` are kept only as the record of
why. Everything below uses `rp=64`.

**Unreproduced baseline, and why.** A first baseline attempt read 436.5 GB/s because it ran
`GRIDMUL=4` (`grid=168×256`). The E1 config is `GRIDMUL=8` → `grid=336×256`. Recorded
because a reader will otherwise find that log and think the baseline is unstable.

## 5. Results

Every number below is from a row whose checksum read `match`/`VALID`.

**DRAM arm, 1.0700 GiB, two runs** (`gm8_run1.log`, `gm8_run2.log`):

| mode | run 1 | run 2 | E1 published |
|---|---:|---:|---:|
| `full` | 522.7 | 519.9 | 516.4 |
| `read` | 743.7 | 715.9 | 717.7 |
| `full_nosgn` | 591.2 | 595.0 | 608.2 |
| `wall_flat` (control) | 715.8 | 671.1 | 668.5 |

`full` reproduces within **+1.2 %**, and the aligned-stream control is 7 % fast today, so
the card is in a slightly faster state overall. The experiment below uses matched runs from
the same session, never the published figures.

**L2 arm, 38.3 MB, `rp=64`, three runs** (`l2rp64_{1,2,3}.log`):

| mode | run 1 | run 2 | run 3 | median |
|---|---:|---:|---:|---:|
| **`full`** | 679.6 | 645.1 | 631.5 | **645.1** |
| `full_nosgn` | 736.8 | 692.3 | 683.1 | 692.3 |
| `read` | 1816.4 | 1556.8 | 1763.9 | 1763.9 (above the wall — L2-served, as intended) |

`read` exceeding 776 GB/s by 2.0–2.3× is the positive control: it proves the footprint is
being served from cache, not DRAM. `full` staying below 776 is why its rows remain VALID
under the harness's own gate.

## 6. Derived

`bpb = 110/256 = 0.4296875 B/weight`; slot rate `168 SIMD32 × 2.802 GHz = 470.7 G wave-instr/s`;
census `C = 193` instruction words per 32 weights per lane (H-2, recounted independently
in §7).

| | GB/s | T weights/s | G wave-instr/s | issue occupancy |
|---|---:|---:|---:|---:|
| DRAM achieved | 521.3 | 1.213 | 228.7 | **48.6 %** |
| L2 (memory-free) ceiling | 645.1 | 1.501 | 283.0 | 60.1 % |
| L2 best run | 679.6 | 1.582 | 298.1 | 63.3 % |
| the wall, for reference | 776.0 | 1.806 | 340.4 | 72.3 % |

- **Memory pressure is worth +23.7 %** (521.3 → 645.1; range +21.1 % to +30.4 % across runs).
  A kernel at issue saturation cannot gain throughput by having memory made free. This
  alone refutes the hypothesis.
- **The instruction count needed to be issue-bound at 521 GB/s is C ≥ 338** instructions per
  32 weights; the kernel has 193, i.e. 57 % of what the 85 %-occupancy claim requires.
- **The two headrooms are almost exactly equal:** +123.8 GB/s from memory (+16.0 % of the
  wall) and +130.9 GB/s from instructions (+16.9 % of the wall). The kernel sits at the
  corner where both bind, and is saturated on neither.
- **Removing the sign path only buys +7.3 % once memory is free** (645.1 → 692.3), although
  it deletes 25 % of the instruction words (48 of 193). So even the memory-free ceiling is
  not issue-limited — cutting a quarter of the instructions does not buy a quarter of the
  time.

## 7. Independent re-derivation of the census (not taken on trust)

`llvm-objdump -d` on `~/a2/iq3s_valid.cpp-hip-amdgcn-amd-amdhsa.hipfb.amdgcn.gfx1100.img`,
counting instruction words in `[0x60BC, 0x65B8]` of `k_full<0,0>`, the range whose eight
`v_dot4_i32_i8` span `0x6218`–`0x6590`:

```
words=193 dots=8 delay=31 globalmem=21
```

`193` independently confirms the probe's census, as do `8` dots and `31` `s_delay_alu`.

## 8. Verdict

**Refuted.** The IQ3_S dequant-GEMV at 516–523 GB/s is **not** VALU-issue-saturated. Issue
occupancy is ~49 % of the slot rate, not ≥ 85 %; relieving memory pressure returns +24 %,
which is impossible under issue saturation; and the emitted body would need 338 instruction
words per 32 weights to saturate issue at this rate, against the 193 it has.

The weaker version of the claim — *the kernel's ceiling is set by instructions as much as
by bytes* — **survives and is now measured**: with memory free the kernel reaches 645 GB/s,
83 % of the 776 wall, so instructions do cap the best case. The two limits are within 6 % of
each other in headroom. What does **not** survive is the note's quantitative framing
(`n ≈ 1.57` against `n ≤ 1.04`, "50 % over budget") and its operational instruction
("memory-side optimisation cannot move this kernel"): memory-side work is worth up to
+124 GB/s.

## 9. What this changes

1. **`DESIGN-instruction-budget.md` §1's `n` model is void** — a unit error of exactly the
   wavefront width (32), as H-2 shows. Its conclusion needs replacing with the measured
   two-bound picture above.
2. **Memory-side work returns to the table**, bounded: prefetch, MLP and layout work can
   reach at most ~645 GB/s here; beyond that instructions bind.
3. **Instruction-side work also remains**, bounded the same way: it can raise the ceiling
   toward 776 but cannot fix the 521 → 645 loss, which is latency/MLP-shaped (the +7.3 %
   from deleting a quarter of the body is the evidence).
4. **A1 is answered; `DESIGN-instruction-budget.md` §"What would falsify this" fired.** The
   note named exactly this outcome as its own refutation and it has occurred.
5. **The rig has no working instruction counter.** Until a working `rocprof`/`rocprofv3` on
   this ROCm build is found, no claim in this project may rest on a hardware counter. The
   differential experiment above is the substitute, and it is stronger: it needs no profiler.
